# LLD — SDKs and tools (`nearpay-node`, `nearpay-agentkit`, `nearpay-cli`, `nearpay-docs`, `nearpay-web`)

> Version 1.2 (step 1.3 implementation findings folded into §1, §2, §6) · Version 1.1 audited (`audits/sdks-and-tools.md`) · Foundations `00-foundations.md` · API conventions

## 1. `@nearpay/node` (Stage 1 subset, full in Stage 2)

- Generated resource clients from `@nearpay/spec` route tables: `nearpay.checkout.sessions.create(params, {idempotencyKey?})`, `paymentIntents`, `refunds`, `paymentLinks`, `customers`, `invoices`, `subscriptions`, `products`, `prices`, `webhookEndpoints`, `events`, `agentPayments`.
- **Stage 1 resource tree (0.1.0, spec 0.1.4):** every spec route callable with a secret/restricted key, plus the anonymous reads a server needs (`webhookSigningKeys.list`, `assets.list`, `x402.supported`); also `settlementDestinations` (read), `x402.{requirements, verify, settle}` and `testHelpers.paymentAttempts.advance`. A unit test fails the build when a new key-callable Stage 1 route appears in `PUBLIC_ROUTES` without a binding.
- Method shape `(pathParam?, bodyOrQuery?, options?)`; delete is `del`. Path params accept `string` (not the `cs_${string}` template type); the API validates. No `Authorization` header on anonymous-only routes (least privilege). No client-side request validation (the API is authoritative; errors carry `request_id`) and no response validation (open enums must be tolerated, api-conventions §5); types still come from the spec schemas.
- Transport: `fetch` with timeout 30 s, automatic `Idempotency-Key` (UUIDv4) on every POST **and** on idempotent PATCH (`updateWebhookEndpoint` declares `idempotent: true`), none on GET/DELETE, reused across up to 2 retries (network errors and timeouts, 409 `idempotency_in_progress`, 429, 5xx; a body cut off mid-stream counts as a network error) with exponential backoff; `Retry-After` honoured up to the backoff cap (8 s); caller aborts are never retried; `NearPay-Version` pinned per client. Results carry a non-enumerable `lastResponse` `{statusCode, requestId, idempotencyKey, idempotentReplayed, attempts}`.
- `nearpay.webhooks.constructEvent(rawBody: string|Buffer, signatureHeader, secret | secret[], {toleranceSec=300})` — verifies `v1` (any of multiple; several secrets for rotation) with constant-time compare; the tolerance is symmetric and inclusive (`|now − t| ≤ 300`); returns `NearPayEvent`, a union derived from `WEBHOOK_TYPES` so `data.object` narrows by `type` (the spec's `Event` types `data.object` as `unknown`). Optional `verifyEd25519(rawBody, header, jwks)` selects the JWK by `kid` when present, else tries every OKP/Ed25519 key; returns `true` or throws. `generateTestHeaderString({payload, secret, timestamp?})` signs payloads for merchants' own tests.
- Packaging: single-package repo; `scripts/release-local.mjs` stages `files` + a manifest without dev fields, packs reproducibly, refuses non-loopback registries and skips an identical republish; `zod` is a peer dependency (as in spec/kit).
- `nearpay.refunds.signers`: helpers that take a refund `next_action` and a merchant-provided signer (viem `Account`, NEAR `KeyPair`) and broadcast — never constructs a different recipient/amount.
- Errors: typed `NearPayError` subclasses by `type`; `requestId` exposed.

## 2. `nearpay-agentkit`

**`@nearpay/x402`** (Stage 1):
- Server middleware (Express, Hono, Next route handler): `paywall({amount, asset?, description?, maxTimeoutSeconds?}, {secretKey})`. Flow: no `PAYMENT-SIGNATURE` → call `POST /x402/requirements` (**one call per 402 response, no caching** — bindings are single-use) → `402` with `PAYMENT-REQUIRED: base64(PaymentRequired)` and body `{}`. With header → decode → `POST /x402/verify` → invalid → `402` with `PAYMENT-RESPONSE` failure; valid → `POST /x402/settle` → success → call handler, set `PAYMENT-RESPONSE: base64(SettlementResponse)`; `settlement_pending` → one retry after 1 s, then `402` with pending response.
- **Paywall local checks** before verify: the payload amount equals the price, and asset / payTo / window equal the configuration when set; `resource.url` must equal this resource when present; the payload is forwarded with `resource` set to the paywall's URL. Facilitator 5xx/network → `503` (`Retry-After: 1`); 4xx (merchant setup, e.g. `account_not_live`) → `500 payment_misconfigured`. Settlement happens before the handler: a handler error after settlement leaves a paid request without the resource.
- **Replay guard (0.1.1):** settle is idempotent on the payload hash and verify results are cached 60 s, so a replayed `PAYMENT-SIGNATURE` would get `success` again (one payment, many deliveries). The paywall remembers settled/settling bindings in process for 10 min (bounded) → `402 requirement_consumed`. Multi-replica merchants need it upstream (agentpay §7; `SettleResponse.replayed` requested for spec 0.1.5).
- Client: `withX402(fetch, signer, {maxAmountPerRequest, allowedPayTo?})` → on 402 picks the NearPay `intents-transfer` requirement, enforces client-side spend limits, signs via `@nearpay/agent-signer`, retries with `PAYMENT-SIGNATURE` once. Spend limits apply to amount + fee (the total debit) in base units: one value for any asset or a per-asset map (unlisted assets refused), optional `allowedPayTo`. A policy refusal throws `AgentSignerError` (never silently returns the 402); non-NearPay 402s are returned untouched.

**`@nearpay/agent-signer`** (Stage 1): `nearSigner({accountId, keyPair, standard?})` (NEP-413 by default, or raw Ed25519; self-verifies the signature, since a KeyPair object could hold another key), `evmSigner(viemAccount)` (ERC-191; normalises v 27/28 → 0/1 and high-s (s → n − s, v ^ 1), and checks the signature recovers to the account), `buildTransferPayment(requirements, signer, {nonceSaltProvider})` → MultiPayload; fetches `current_salt` via RPC (cached 60 s). x402 payloads use `deadline = now + floor(maxTimeoutSeconds / 2)` (requirements carry no absolute expiry; agentpay §6). For NearPay **checkout** requirements it first obtains and verifies a sentinel attestation and refuses to sign on mismatch: Ed25519 over JCS of the attestation as received (no schema stripping before verifying), `kid` allow-list, key `not_after`, `v`/kind/attempt/livemode equal, every requirement field equal (deadline as an instant), `destination.asset_id == token`, `expires_at > now`; the agent signs the attested requirement. Order: requirements → spend policy → sentinel → verify → sign → submit. x402 requirements come from the merchant's own server and are signed as received (client spend limits apply).
- **Pinned sentinel keys:** `PINNED_SENTINEL_KEYS` ships **empty** in 0.1.x: in Stages 1–4 sentinel's key is generated per stack (`seed.sh keys`), and baking it into the tarball would break reproducible packing and consumers' lockfile integrity. Operators pin keys with the `pinnedKeys` option, read out of band from `.secrets/public/sentinel_keys.json` (`parsePinnedKeys`); keys are never fetched from `/v1/attestations/keys`. No pinned key → every checkout payment is refused (`no_pinned_keys`). Production kids go into the package at Stage 5.
- `parseCheckoutUrl` takes `…/c/<cs>` or `…/embed/<cs>` with the client secret in the fragment; the API base defaults to `<origin>/api` (same-origin gateway, platform §1).
- **Packages:** both depend only on `@nearpay/spec` (+ noble, bs58, canonicalize); ESM-only exports (`import` condition) like the kit; `@nearpay/x402/hono` is a subpath so non-Hono users never load Hono types. Published at 0.1.1.

**`@nearpay/mcp`** (Stage 3): MCP server (stdio + streamable HTTP) with tools `nearpay_create_checkout_session`, `nearpay_get_payment_intent`, `nearpay_list_payments` (merchant key), and payer tools `nearpay_pay_checkout_session(session_url)` and `nearpay_fetch_paid(url)` (uses `withX402` with a configured signer and budget).

## 3. `nearpay-cli` (Stage 3)

Commands: `login` (device code via dashboard session → restricted test key stored in OS keychain), `listen --forward-to http://localhost:3000/webhooks` (consumes `GET /v1/events/stream`, re-signs with a local secret printed at start), `trigger <scenario>` (creates a test session and advances the sandbox), `events list|resend`, `logs tail`. Distributed via npm (`@nearpay/cli`) and single-file binaries (`bun build --compile`).

## 4. `nearpay-docs` (Stage 2; Stage 1 = READMEs)

Astro Starlight site: guides (quickstart, checkout, webhooks, test mode, refunds, agents/x402, settlement destinations), API reference rendered from `nearpay-spec/openapi/public.yaml`, error pages generated from the error catalogue, webhook IP list, changelog. Built statically; deployed with the stack.

## 5. `nearpay-web` (Stage 5)

Astro static marketing site at `nearpay.money`: product, pricing (from fee schedule doc), legal pages (terms incl. 1Click flow-down provisions, privacy), status link.

## 6. Tests

SDK: contract tests against spec fixtures; webhook and agent-signer vectors from `nearpay-spec/test-vectors` (same files used by `nearpay-webhooks` and `nearpay-agentpay`); x402 middleware E2E against sandbox in testbed. **Contract-test pattern for SDKs:** a ~60-line fake gateway maps `Bearer sk_test_…` to `mintTestToken({ptype: "secret_key"})` and forwards to kit `mockPeer` per owning service, so the real service bootstrap validates requests and checks responses without containers (`mockPeer` handlers must be `async`).
