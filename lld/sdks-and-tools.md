## 1. `@nearpay/node` (Stage 1 subset, full in Stage 2)

- Generated resource clients from `@nearpay/spec` route tables: `nearpay.checkout.sessions.create(params, {idempotencyKey?})`, `paymentIntents`, `refunds`, `paymentLinks`, `customers`, `invoices`, `subscriptions`, `products`, `prices`, `webhookEndpoints`, `events`, `agentPayments`.
- **Stage 1 resource tree (0.1.0, spec 0.1.4):** every spec route callable with a secret/restricted key, plus the anonymous reads a server needs (`webhookSigningKeys.list`, `assets.list`, `x402.supported`); also `settlementDestinations` (read), `x402.{requirements, verify, settle}` and `testHelpers.paymentAttempts.advance`. A unit test fails the build when a new key-callable Stage 1 route appears in `PUBLIC_ROUTES` without a binding. Step 1.4 (spec 0.1.5) binds `webhookEndpoints.listDeliveries(id, query)` (`WebhookDelivery`, `whd_…`); `getDashboardSession` and `challengeSettlementDestination` are session-only and stay unbound.
- Method shape `(pathParam?, bodyOrQuery?, options?)`; delete is `del`. Path params accept `string` (not the `cs_${string}` template type); the API validates. No `Authorization` header on anonymous-only routes (least privilege). No client-side request validation (the API is authoritative; errors carry `request_id`); types come from the spec schemas.
- **Stage 2 tree (0.2.0, spec 0.2.0, step 2.3):** adds `paymentIntents.{create, review}`, `refunds.{create, retrieve, list, prepare, submitTx, cancel}` (+ `signers`), `paymentLinks.{create, retrieve, list, update}`, `customers.{create, retrieve, list, update, del}`, `webhookEndpoints.rotateSecret`, `events.resend`, `testHelpers.refunds.simulateDeposit`. The build test now covers every key-callable public route (all stages). Not bound because spec 0.2.0 admits only a dashboard session: API keys (incl. restricted-key creation), account, KYB, team/invitations, destination writes, `updateRefundRecipient`. Restricted keys: `restrictedKeyScope(method)` / `scopesFor(methods)` from the routes' `restricted_key:<scope>`; a 403 of an `rk_` client carries `requiredScope`.
- **Lists (step 2.3):** list methods return a `ListPromise` — `await` = first page; `for await` / `autoPagingToArray({limit ≤ 10 000})` / `autoPagingEach` follow `starting_after` (or `ending_before` when the first call used it), keeping filters. Queries accept range keys flat (`created[gte]`) or grouped (`created: {gte}`), and `metadata: {k: v}` → `metadata[k]=v` where the route uses `withMetadataFilter` (ADR-0018).
- **Response parsing (step 2.3, reverses "no response validation"):** every response is parsed with the route schema via `safeParseTolerant`; unknown open-enum values and unknown event types (checked against `EventEnvelopeLoose`, also per item of a page) are kept and listed in `lastResponse.unknownEnumValues`. `responseValidation`: `tolerant` (default) returns a contract-breaking body **as received** and reports it (`lastResponse.validationIssues`, `onValidationIssue`, else one process warning per route) — a 2xx write already changed state, and throwing would invite a retry with a fresh key (duplicate refund); `strict` throws `NearPayResponseValidationError` carrying the `idempotencyKey`; `off` = 0.1 behaviour. `constructEvent` / `parseEvent` use the same modes (`validation`). Safety-critical refund `next_action`s are always validated (below).
- Transport: `fetch` with timeout 30 s, automatic `Idempotency-Key` (UUIDv4) on every POST **and** on idempotent PATCH, none on GET/DELETE, reused across up to 2 retries with exponential backoff; `Retry-After` honoured up to the backoff cap (8 s); caller aborts are never retried; `NearPay-Version` pinned per client. **Retry policy (step 2.3):** a status/code is retryable per the error catalogue's `retryable` (unknown codes: 429/5xx); 429, 409 `idempotency_in_progress` and connections refused before sending (ECONNREFUSED/ENOTFOUND/EAI_AGAIN/…) are retried for any route; 5xx, timeouts, dropped connections and cut-off bodies only for replay-safe routes (GET, DELETE, `idempotent: true`) — so the x402 POSTs (`idempotent: false`) are not repeated after the server may have acted. Errors expose `retryable`. Results carry a non-enumerable `lastResponse` `{statusCode, requestId, idempotencyKey, idempotentReplayed, attempts, unknownEnumValues, validationIssues}`.
- `nearpay.webhooks.constructEvent(rawBody: string|Buffer, signatureHeader, secret | secret[], {toleranceSec=300})` — verifies `v1` (any of multiple; several secrets for rotation) with constant-time compare; the tolerance is symmetric and inclusive (`|now − t| ≤ 300`); returns the spec's `TypedEvent` (`NearPayEvent` alias) so `data.object` narrows by `type`. **Rotation overlap (step 2.3):** secrets may be `{secret, expiresAt}` entries (`expiresAt` = `previous_secret_expires_at`); an entry is accepted while `now ≤ expiresAt`, so `[new, {old, expiresAt}]` accepts both during the overlap and only the new one afterwards; `generateTestHeaderString` signs with several secrets like a rotation delivery. Optional `verifyEd25519(rawBody, header, jwks)` selects the JWK by `kid` when present, else tries every OKP/Ed25519 key; returns `true` or throws. `generateTestHeaderString({payload, secret, timestamp?})` signs payloads for merchants' own tests.
- Packaging: single-package repo; `scripts/release-local.mjs` stages `files` + a manifest without dev fields, packs reproducibly, refuses non-loopback registries and skips an identical republish; `zod` is a peer dependency (as in spec/kit).
- `nearpay.refunds.signers`: helpers that take a refund `next_action` and a merchant-provided signer (viem `Account`, NEAR `KeyPair`) and broadcast — never constructs a different recipient/amount. **Step 2.3:** zero runtime deps (structural signers; base58, NEP-413 borsh hash, ERC-191 v/low-s normalisation and ERC-20 calldata in-house). `check(refund)` before anything is signed: status `requires_action`, `next_action` parsed (tolerant), current leg `awaiting_signature` with no `submitted_tx` and `leg.amount` = action amount, deadline ≥ 60 s ahead; `sign_intent`: `payload`, `nep413.message` and `message` encode the same single transfer as `transfer` (receiver, `{token: amount}`, memo), same nonce/signer, `intents.near`, deadline ±1 s, `transfer.token = refund.asset_id`, and for `intents_transfer` refunds `receiver_id = recipient.address` (INV-7); `sign_and_send`: `asset_id = refund.asset_id`. Signers: `nearKeyPair` (NEP-413 preferred, else raw ed25519; self-verifies, and checks the key of an implicit `signer_id`), `evmAccount` (ERC-191, address = `signer_id`; signature verified by payments/Verifier — no keccak/secp256k1 in Node core), `evmWallet` (viem WalletClient: account = `from`, chain id from CAIP-2 `eip155:<id>`, native or ERC-20, memo refused), or any `TransferSender`. `signAndSubmit(refund | id, signer)` submits with key `<re>-leg-<n>-submit`; if reporting fails after a broadcast it throws `submit_failed` with `txHash` (never re-broadcasts).
- Errors: typed `NearPayError` subclasses by `type`; `requestId` exposed.

## 2. `nearpay-agentkit`

**`@nearpay/x402`** (Stage 1):
- Server middleware (Express, Hono, Next route handler): `paywall({amount, asset?, description?, maxTimeoutSeconds?}, {secretKey})`. Flow: no `PAYMENT-SIGNATURE` → call `POST /x402/requirements` (**one call per 402 response, no caching** — bindings are single-use) → `402` with `PAYMENT-REQUIRED: base64(PaymentRequired)` and body `{}`. With header → decode → `POST /x402/verify` → invalid → `402` with `PAYMENT-RESPONSE` failure; valid → `POST /x402/settle` → success → call handler, set `PAYMENT-RESPONSE: base64(SettlementResponse)`; `settlement_pending` → one retry after 1 s, then `402` with pending response.
- **Paywall local checks** before verify: the payload amount equals the price, and asset / payTo / window equal the configuration when set; `resource.url` must equal this resource when present; the payload is forwarded with `resource` set to the paywall's URL. Facilitator 5xx/network → `503` (`Retry-After: 1`); 4xx (merchant setup, e.g. `account_not_live`) → `500 payment_misconfigured`. Settlement happens before the handler: a handler error after settlement leaves a paid request without the resource.
- **Replay guard (0.1.1):** settle is idempotent on the payload hash and verify results are cached 60 s, so a replayed `PAYMENT-SIGNATURE` would get `success` again (one payment, many deliveries). The paywall remembers settled/settling bindings in process for 10 min (bounded) → `402 requirement_consumed`. Across replicas (and after the 10 min) agentpay flags repeats with `SettleResponse.replayed` (spec 0.1.5, agentpay §7): the paywall refuses **every** replayed success with `402 requirement_consumed` (the handler and `onSettled` do not run; the binding is remembered), including the retry after its own `settlement_pending` — agentpay's pending answers never claim the result, so a replayed retry means another request already got the final result (lead decision, 2026-11-07).
- Client: `withX402(fetch, signer, {maxAmountPerRequest, allowedPayTo?})` → on 402 picks the NearPay `intents-transfer` requirement, enforces client-side spend limits, signs via `@nearpay/agent-signer`, retries with `PAYMENT-SIGNATURE` once; `onPayment` also receives `settlement` (decoded `PAYMENT-RESPONSE`) and `replayed`, so a replay is not counted as a new payment. Spend limits apply to amount + fee (the total debit) in base units: one value for any asset or a per-asset map (unlisted assets refused), optional `allowedPayTo`. A policy refusal throws `AgentSignerError` (never silently returns the 402); non-NearPay 402s are returned untouched.

**`@nearpay/agent-signer`** (Stage 1): `nearSigner({accountId, keyPair, standard?})` (NEP-413 by default, or raw Ed25519; self-verifies the signature, since a KeyPair object could hold another key), `evmSigner(viemAccount)` (ERC-191; normalises v 27/28 → 0/1 and high-s (s → n − s, v ^ 1), and checks the signature recovers to the account), `buildTransferPayment(requirements, signer, {nonceSaltProvider})` → MultiPayload; fetches `current_salt` via RPC (cached 60 s). x402 payloads are signed with exactly the requirement's `extra.deadline` (spec 0.1.5; `x402LatestDeadline`, milliseconds kept, not clamped to the local clock); requirements without it fall back to `deadline = now + floor(maxTimeoutSeconds / 2)` (agentpay §6). An explicit `deadline` option past the requirement's limit is refused. For NearPay **checkout** requirements it first obtains and verifies a sentinel attestation and refuses to sign on mismatch: Ed25519 over JCS of the attestation as received (no schema stripping before verifying), `kid` allow-list, key `not_after`, `v`/kind/attempt/livemode equal, every requirement field equal (deadline as an instant), `destination.asset_id == token`, `expires_at > now`; the agent signs the attested requirement. Order: requirements → spend policy → sentinel → verify → sign → submit. x402 requirements come from the merchant's own server and are signed as received (client spend limits apply).
- **Pinned sentinel keys:** `PINNED_SENTINEL_KEYS` ships **empty** in 0.1.x: in Stages 1–4 sentinel's key is generated per stack (`seed.sh keys`), and baking it into the tarball would break reproducible packing and consumers' lockfile integrity. Operators pin keys with the `pinnedKeys` option, read out of band from `.secrets/public/sentinel_keys.json` (`parsePinnedKeys`); keys are never fetched from `/v1/attestations/keys`. No pinned key → every checkout payment is refused (`no_pinned_keys`). Production kids go into the package at Stage 5.
- `parseCheckoutUrl` takes `…/c/<cs>` or `…/embed/<cs>` with the client secret in the fragment; the API base defaults to `<origin>/api` (same-origin gateway, platform §1).
- **Packages:** both depend only on `@nearpay/spec` (+ noble, bs58, canonicalize); ESM-only exports (`import` condition) like the kit; `@nearpay/x402/hono` is a subpath so non-Hono users never load Hono types. Published at 0.1.1.
- **Tolerant parsing (spec 0.1.5):** API responses (agent-signer `callRoute`, the x402 facilitator client) and the `PAYMENT-REQUIRED` / `PAYMENT-RESPONSE` headers are parsed with `safeParseTolerant`, so a new open-enum value (attempt status, `invalidReason`, `errorReason`) is passed on instead of failing; closed enums, literals and shapes still fail. Sentinel attestations stay strictly validated.

**`@nearpay/mcp`** (Stage 3): MCP server (stdio + streamable HTTP) with tools `nearpay_create_checkout_session`, `nearpay_get_payment_intent`, `nearpay_list_payments` (merchant key), and payer tools `nearpay_pay_checkout_session(session_url)` and `nearpay_fetch_paid(url)` (uses `withX402` with a configured signer and budget).

## 3. `nearpay-cli` (Stage 3)

## 4. `nearpay-site` — docs (Stage 2; Stage 1 = READMEs)

One Astro project (ADR-0019) builds both public sites: `dist/docs` → `docs.<domain>`, `dist/web` → apex domain.

Guides (quickstart, checkout hosted/embedded/payment links, payment intents + list filters, refunds, customers, settlement destinations, webhooks, test mode, agents/x402), API reference rendered from `nearpay-spec/openapi/public.yaml`, error pages generated from the error catalogue, webhook IP list, changelog. Built statically; deployed with the stack.

**Step 2.3 decisions (implemented):**
- **No Starlight.** Starlight injects an inline theme script and Pagefind needs `wasm-unsafe-eval`, both incompatible with the strict CSP (`default-src 'none'; script-src 'self'; style-src 'self'`), and its styling would fight the `@nearpay-internal/ui` tokens. The docs use a small custom Astro layout on the kit's tokens, DM Sans and component CSS. Code blocks use Prism (class-based tokens; Shiki writes `style=""`). Astro never inlines CSS or scripts (`inlineStylesheets: never`, `assetsInlineLimit: 0`); `scripts/check-dist.mjs` fails the build on any inline script/style, style attribute, inline handler or third-party asset.
- **Two builds, one project:** `NP_SITE=web|docs` selects `src/routes/<site>/`, injected with `injectRoute` (no `src/pages`). Docs are served at the root of `docs.<domain>` so catalogue `doc_url`s (`/errors/<code>`) resolve.
- **Generated pages are rendered at build time** from the installed `@nearpay/spec` (`src/lib/spec.ts`): nothing generated is committed, so nothing can be hand-edited. `check-dist` asserts one page per catalogue code and that every public developer route appears in the reference.
- **Reference scope:** routes whose `x-nearpay.auth` includes a non-session credential (secret/restricted key, client secret, anonymous), except `/v1/auth/*`. Dashboard-session-only routes (account, team, API keys, settlement-destination changes, refund recipient override) are the dashboard's API and are not listed. Spec 0.2.0: 62 routes in 15 presentation groups (resource names; grouping and intros are presentation only).
- Event types page from `WEBHOOK_TYPES`; per-error "What to do" advice is hand-written (`error-notes.ts`), facts come from the catalogue. Search: a static `/search-index.json` (guides, groups, operations, error codes) and a 1.5 KB gz external script (also copy buttons); every page works without JavaScript (nested attributes and mobile navigation use `<details>`).
- **Webhook IP list:** not published yet (no production egress IPs); the webhooks guide says so and recommends signature verification.

## 6. Tests

SDK: contract tests against spec fixtures (node: every method also against an in-process spec-validating mock with strict request parsing, idempotent replay and response-schema checks, `test/support/spec-mock.ts`); webhook and agent-signer vectors from `nearpay-spec/test-vectors` (same files used by `nearpay-webhooks` and `nearpay-agentpay`); x402 middleware E2E against sandbox in testbed. **Contract-test pattern for SDKs:** a ~60-line fake gateway maps `Bearer sk_test_…` to `mintTestToken({ptype: "secret_key"})` and forwards to kit `mockPeer` per owning service, so the real service bootstrap validates requests and checks responses without containers (`mockPeer` handlers must be `async`).
