## 1. `@nearpay/node` (Stage 1 subset, full in Stage 2)

- Generated resource clients from `@nearpay/spec` route tables: `nearpay.checkout.sessions.create(params, {idempotencyKey?})`, `paymentIntents`, `refunds`, `paymentLinks`, `customers`, `invoices`, `subscriptions`, `products`, `prices`, `webhookEndpoints`, `events`, `agentPayments`.
- **Stage 1 resource tree (0.1.0, spec 0.1.4):** every spec route callable with a secret/restricted key, plus the anonymous reads a server needs (`webhookSigningKeys.list`, `assets.list`, `x402.supported`); also `settlementDestinations` (read), `x402.{requirements, verify, settle}` and `testHelpers.paymentAttempts.advance`. A unit test fails the build when a new key-callable Stage 1 route appears in `PUBLIC_ROUTES` without a binding. Step 1.4 (spec 0.1.5) binds `webhookEndpoints.listDeliveries(id, query)` (`WebhookDelivery`, `whd_…`); `getDashboardSession` and `challengeSettlementDestination` are session-only and stay unbound.
- Method shape `(pathParam?, bodyOrQuery?, options?)`; delete is `del`. Path params accept `string` (not the `cs_${string}` template type); the API validates. No `Authorization` header on anonymous-only routes (least privilege). No client-side request validation (the API is authoritative; errors carry `request_id`); types come from the spec schemas.
- **Stage 2 tree (0.2.0, spec 0.2.0, step 2.3):** adds `paymentIntents.{create, review}`, `refunds.{create, retrieve, list, prepare, submitTx, cancel}` (+ `signers`), `paymentLinks.{create, retrieve, list, update}`, `customers.{create, retrieve, list, update, del}`, `webhookEndpoints.rotateSecret`, `events.resend`, `testHelpers.refunds.simulateDeposit`. The build test now covers every key-callable public route (all stages). Not bound because spec 0.2.0 admits only a dashboard session: API keys (incl. restricted-key creation), account, KYB, team/invitations, destination writes, `updateRefundRecipient`. Restricted keys: `restrictedKeyScope(method)` / `scopesFor(methods)` from the routes' `restricted_key:<scope>`; a 403 of an `rk_` client carries `requiredScope`.
- **Lists (step 2.3):** list methods return a `ListPromise` — `await` = first page; `for await` / `autoPagingToArray({limit ≤ 10 000})` / `autoPagingEach` follow `starting_after` (or `ending_before` when the first call used it), keeping filters. Queries accept range keys flat (`created[gte]`) or grouped (`created: {gte}`), and `metadata: {k: v}` → `metadata[k]=v` where the route uses `withMetadataFilter` (ADR-0018).
- **Response parsing (step 2.3, reverses "no response validation"):** every response is parsed with the route schema via `safeParseTolerant`; unknown open-enum values and unknown event types (checked against `EventEnvelopeLoose`, also per item of a page) are kept and listed in `lastResponse.unknownEnumValues`. `responseValidation`: `tolerant` (default) returns a contract-breaking body **as received** and reports it (`lastResponse.validationIssues`, `onValidationIssue`, else one process warning per route) — a 2xx write already changed state, and throwing would invite a retry with a fresh key (duplicate refund); `strict` throws `NearPayResponseValidationError` carrying the `idempotencyKey`; `off` = 0.1 behaviour. `constructEvent` / `parseEvent` use the same modes (`validation`). Safety-critical refund `next_action`s are always validated (below).
- Transport: `fetch` with timeout 30 s, automatic `Idempotency-Key` (UUIDv4) on every POST **and** on idempotent PATCH, none on GET/DELETE, reused across up to 2 retries with exponential backoff; `Retry-After` honoured up to the backoff cap (8 s); caller aborts are never retried; `NearPay-Version` pinned per client. **Retry policy (step 2.3):** a status/code is retryable per the error catalogue's `retryable` (unknown codes: 429/5xx); 429, 409 `idempotency_in_progress` and connections refused before sending (ECONNREFUSED/ENOTFOUND/EAI_AGAIN/…) are retried for any route; 5xx, timeouts, dropped connections and cut-off bodies only for replay-safe routes (GET, DELETE, `idempotent: true`) — so the x402 POSTs (`idempotent: false`) are not repeated after the server may have acted. Errors expose `retryable`. Results carry a non-enumerable `lastResponse` `{statusCode, requestId, idempotencyKey, idempotentReplayed, attempts, unknownEnumValues, validationIssues}`.
- `nearpay.webhooks.constructEvent(rawBody: string|Buffer, signatureHeader, secret | secret[], {toleranceSec=300})` — verifies `v1` (any of multiple; several secrets for rotation) with constant-time compare; the tolerance is symmetric and inclusive (`|now − t| ≤ 300`); returns the spec's `TypedEvent` (`NearPayEvent` alias) so `data.object` narrows by `type`. **Rotation overlap (step 2.3):** secrets may be `{secret, expiresAt}` entries (`expiresAt` = `previous_secret_expires_at`); an entry is accepted while `now ≤ expiresAt`, so `[new, {old, expiresAt}]` accepts both during the overlap and only the new one afterwards; `generateTestHeaderString` signs with several secrets like a rotation delivery. Optional `verifyEd25519(rawBody, header, jwks)` selects the JWK by `kid` when present, else tries every OKP/Ed25519 key; returns `true` or throws. `generateTestHeaderString({payload, secret, timestamp?})` signs payloads for merchants' own tests.
- Packaging: single-package repo; `scripts/release-local.mjs` stages `files` + a manifest without dev fields, packs reproducibly, refuses non-loopback registries and skips an identical republish; `zod` is a peer dependency (as in spec/kit).
- `nearpay.refunds.signers`: helpers that take a refund `next_action` and a merchant-provided signer (viem `Account`, NEAR `KeyPair`) and broadcast — never constructs a different recipient/amount. **Step 2.3:** zero runtime deps (structural signers; base58, NEP-413 borsh hash, ERC-191 v/low-s normalisation and ERC-20 calldata in-house). `check(refund)` before anything is signed: status `requires_action`, `next_action` parsed (tolerant), current leg `awaiting_signature` with no `submitted_tx` and `leg.amount` = action amount, deadline ≥ 60 s ahead; `sign_intent`: `payload`, `nep413.message` and `message` encode the same single transfer as `transfer` (receiver, `{token: amount}`, memo), same nonce/signer, `intents.near`, deadline ±1 s, `transfer.token = refund.asset_id`, and for `intents_transfer` refunds `receiver_id = recipient.address` (INV-7); `sign_and_send`: `asset_id = refund.asset_id`. Signers: `nearKeyPair` (NEP-413 preferred, else raw ed25519; self-verifies, and checks the key of an implicit `signer_id`), `evmAccount` (ERC-191, address = `signer_id`; signature verified by payments/Verifier — no keccak/secp256k1 in Node core), `evmWallet` (viem WalletClient: account = `from`, chain id from CAIP-2 `eip155:<id>`, native or ERC-20, memo refused), or any `TransferSender`. `signAndSubmit(refund | id, signer)` submits with key `<re>-leg-<n>-submit`; if reporting fails after a broadcast it throws `submit_failed` with `txHash` (never re-broadcasts).
- Errors: typed `NearPayError` subclasses by `type`; `requestId` exposed.

### 1.1 Stage 3 (step 3.3, `@nearpay/node` 0.3.0, spec 0.3.0) — implemented

- **Tree:** `products`, `prices`, `taxRates` (create/retrieve/list/update), `invoices` (create/retrieve/list/update/`del`/`finalize`/`send`/`void`/`markUncollectible`/`pdf`), `subscriptions` (create/retrieve/list/update/`cancel`), `x402.nearIntents.{requirements, verify, settle}`, `testHelpers.checkoutSessions.pay`, `events.stream`. Not bound: hosted-invoice payer routes (`/v1/invoices/{id}/public/**`, invoice secret) and CLI login (anonymous device flow / session approval). Every key-callable route of 0.3.0 has a restricted-key scope (incl. the sandbox helpers), so `scopesFor` never needs a secret key now.
- **Binary routes** (`binaryResponse`): `Accept: <contentType>, application/json`; success → `Uint8Array` with non-enumerable `lastResponse`, `contentType`, `filename` (from `Content-Disposition`, RFC 5987 aware); errors stay JSON; a 2xx with another content type is a validation issue handled by `responseValidation` (tolerant: returned + reported; strict: throws). Replay-safe like any GET.
- **`events.stream(params?, options?)`** (`streamEvents` is dispatched by `bindRoute` on `route.stream`): async iterator of `TypedEvent`s, single consumer. Every connection sends the cursor as `Last-Event-ID` (initially the caller's `starting_after`, then the last yielded id; the query `starting_after` is never sent); duplicate ids dropped (last 10 000); `reset` → `onReset` (default one warning) and the bad cursor is forgotten so the next reconnect is live-only; clean server close → wait the server's `retry:` (3 s); errors (connection, idle > 45 s without bytes, 429, 5xx) → backoff 1 s → 30 s with jitter, `Retry-After` honoured up to the cap; 400/401/403/404 end the iteration by throwing (live keys: `403 livemode_forbidden`). Frames parsed with `safeParseTolerant` per the client's validation mode. `Transport.connect` opens the SSE response (connect timeout = client timeout, no retries).
- **Retry policy amendment (node CR "x402Verify/x402Settle idempotent", spec 0.2.1 note):** `x402Verify` is treated as replay-safe (`REPLAY_SAFE_POSTS`; no state change, cached 60 s) and retried after 5xx/timeouts with the same key. `x402Settle` stays un-retried after an unknown outcome: a repeat answers `replayed: true`, which a paywall must treat as already delivered, and the SDK cannot tell its own earlier attempt from another request's. `x402NearIntentsVerify` issues a quote and is not repeated either.
- **Webhooks:** the 12 billing types come typed from the spec's `WEBHOOK_TYPES`/`TypedEvent` (no SDK code); tested per type. The spec's normative tax functions (`computeLineTax`, `computeInvoiceTotals`, `taxPercentageToPpm`) are re-exported for previews.
- **Known spec issue (CR for 0.3.1):** `TypedEvent = Omit<Event, "type" | "data"> & …` over the loose (index-signature) `Event` loses the envelope keys — `event.id`, `created`, `livemode` are typed `unknown`. Fix in the spec with a known-keys `Omit`; the SDK keeps returning the spec type.

## 2. `nearpay-agentkit`

**`@nearpay/x402`** (Stage 1):
- Server middleware (Express, Hono, Next route handler): `paywall({amount, asset?, description?, maxTimeoutSeconds?}, {secretKey})`. Flow: no `PAYMENT-SIGNATURE` → call `POST /x402/requirements` (**one call per 402 response, no caching** — bindings are single-use) → `402` with `PAYMENT-REQUIRED: base64(PaymentRequired)` and body `{}`. With header → decode → `POST /x402/verify` → invalid → `402` with `PAYMENT-RESPONSE` failure; valid → `POST /x402/settle` → success → call handler, set `PAYMENT-RESPONSE: base64(SettlementResponse)`; `settlement_pending` → one retry after 1 s, then `402` with pending response.
- **Paywall local checks** before verify: the payload amount equals the price, and asset / payTo / window equal the configuration when set; `resource.url` must equal this resource when present; the payload is forwarded with `resource` set to the paywall's URL. Facilitator 5xx/network → `503` (`Retry-After: 1`); 4xx (merchant setup, e.g. `account_not_live`) → `500 payment_misconfigured`. Settlement happens before the handler: a handler error after settlement leaves a paid request without the resource.
- **Replay guard (0.1.1):** settle is idempotent on the payload hash and verify results are cached 60 s, so a replayed `PAYMENT-SIGNATURE` would get `success` again (one payment, many deliveries). The paywall remembers settled/settling bindings in process for 10 min (bounded) → `402 requirement_consumed`. Across replicas (and after the 10 min) agentpay flags repeats with `SettleResponse.replayed` (spec 0.1.5, agentpay §7): the paywall refuses **every** replayed success with `402 requirement_consumed` (the handler and `onSettled` do not run; the binding is remembered), including the retry after its own `settlement_pending` — agentpay's pending answers never claim the result, so a replayed retry means another request already got the final result (lead decision, 2026-11-07).
- Client: `withX402(fetch, signer, {maxAmountPerRequest, allowedPayTo?})` → on 402 picks the NearPay `intents-transfer` requirement, enforces client-side spend limits, signs via `@nearpay/agent-signer`, retries with `PAYMENT-SIGNATURE` once; `onPayment` also receives `settlement` (decoded `PAYMENT-RESPONSE`) and `replayed`, so a replay is not counted as a new payment. Spend limits apply to amount + fee (the total debit) in base units: one value for any asset or a per-asset map (unlisted assets refused), optional `allowedPayTo`. A policy refusal throws `AgentSignerError` (never silently returns the 402); non-NearPay 402s are returned untouched.

**`@nearpay/agent-signer`** (Stage 1): `nearSigner({accountId, keyPair, standard?})` (NEP-413 by default, or raw Ed25519; self-verifies the signature, since a KeyPair object could hold another key), `evmSigner(viemAccount)` (ERC-191; normalises v 27/28 → 0/1 and high-s (s → n − s, v ^ 1), and checks the signature recovers to the account), `buildTransferPayment(requirements, signer, {nonceSaltProvider})` → MultiPayload; fetches `current_salt` via RPC (cached 60 s). x402 payloads are signed with exactly the requirement's `extra.deadline` (spec 0.1.5; `x402LatestDeadline`, milliseconds kept, not clamped to the local clock); requirements without it fall back to `deadline = now + floor(maxTimeoutSeconds / 2)` (agentpay §6). An explicit `deadline` option past the requirement's limit is refused. For NearPay **checkout** requirements it first obtains and verifies a sentinel attestation and refuses to sign on mismatch: Ed25519 over JCS of the attestation as received (no schema stripping before verifying), `kid` allow-list, key `not_after`, `v`/kind/attempt/livemode equal, every requirement field equal (deadline as an instant), `destination.asset_id == token`, `expires_at > now`; the agent signs the attested requirement. Order: requirements → spend policy → sentinel → verify → sign → submit. x402 requirements come from the merchant's own server and are signed as received (client spend limits apply).
- **Pinned sentinel keys:** `PINNED_SENTINEL_KEYS` ships **empty** in 0.1.x: in Stages 1–4 sentinel's key is generated per stack (`seed.sh keys`), and baking it into the tarball would break reproducible packing and consumers' lockfile integrity. Operators pin keys with the `pinnedKeys` option, read out of band from `.secrets/public/sentinel_keys.json` (`parsePinnedKeys`); keys are never fetched from `/v1/attestations/keys`. No pinned key → every checkout payment is refused (`no_pinned_keys`). Production kids go into the package at Stage 5.
- `parseCheckoutUrl` takes `…/c/<cs>` or `…/embed/<cs>` with the client secret in the fragment; the API base defaults to `<origin>/api` (same-origin gateway, platform §1).
- **Packages:** both depend only on `@nearpay/spec` (+ noble, bs58, canonicalize); ESM-only exports (`import` condition) like the kit; `@nearpay/x402/hono` is a subpath so non-Hono users never load Hono types. Published at 0.1.1.
- **Tolerant parsing (spec 0.1.5):** API responses (agent-signer `callRoute`, the x402 facilitator client) and the `PAYMENT-REQUIRED` / `PAYMENT-RESPONSE` headers are parsed with `safeParseTolerant`, so a new open-enum value (attempt status, `invalidReason`, `errorReason`) is passed on instead of failing; closed enums, literals and shapes still fail. Sentinel attestations stay strictly validated.

**`@nearpay/mcp`** (Stage 3): MCP server (stdio + streamable HTTP) with tools `nearpay_create_checkout_session`, `nearpay_get_payment_intent`, `nearpay_list_payments` (merchant key), and payer tools `nearpay_pay_checkout_session(session_url)` and `nearpay_fetch_paid(url)` (uses `withX402` with a configured signer and budget).

**Stage 3 contracts (spec 0.3.0) — no new server routes for agentkit.**
- **Cross-chain x402 (`near-intents`, agentpay §3.1).** Paywall: `paywall({…, origins?: [{asset_id, max_timeout_s?}]})` — with origins it calls `POST /x402/near-intents/requirements` (one call per 402, both methods in one `X402PaymentRequiredAny`), dispatches by `accepted.extra.assetTransferMethod`: `intents-transfer` → `/x402/verify|settle` as before; `near-intents` `quote` → `/x402/near-intents/verify`, then a second 402 with `quotedRequirements(entry, extra)` (never serves); `deposit` → `/x402/near-intents/settle` before the handler, `settlement_pending` → `402` with the pending `PAYMENT-RESPONSE` (no 1 s retry: cross-chain takes minutes). `paymentRequirements` is always the paywall's **own** unquoted entry for `accepted.network`/`accepted.asset`, matched by `extra.binding`. The paywall marks an operation executed (settled bindings, in process + `replayed`) and answers repeats with `402 exact_near_intents_operation_executed`. Client: `withX402(fetch, signer, {…, crossChain?: {originSigner, refundTo, origins?}})` prefers `intents-transfer` when the signer has an Intents balance, else picks a `near-intents` entry whose origin it can pay; spend limits apply to the **quoted** `amount` (origin units) before depositing; it persists `{payTo, depositMemo, operationToken}` before depositing and the `txHash` after (pluggable store), retries the deposit payload with the same token until a final result (backoff 5 s → 30 s, bounded by `refundDeadline` + 24 h), and never funds a second quote while one is pending. Header parsing uses `X402PaymentRequiredAny` / `NearIntentsSettleResponse` with `safeParseTolerant`.
- **MCP pay tools.** `nearpay_fetch_paid(url, {max_amount, cross_chain?})` wraps the client above (both methods). `nearpay_pay_checkout_session(url)` accepts a checkout URL (`…/c/<cs>#<client secret>`) **or a hosted invoice URL `…/i/<in_…>#<invoice secret>`** (FR-AGT-05): for an invoice it calls billing `createPublicInvoiceSession` `POST /v1/invoices/{id}/public/sessions` with `X-NearPay-Invoice-Secret` and continues with the returned `{checkout_session, client_secret}` through the existing `agent_pay/requirements` → sentinel attestation → sign → `agent_pay` flow (no new contract). Merchant tools use the merchant key with the node SDK; the MCP server holds no NearPay credentials beyond those configured.

**Step 3.3 implementation decisions (agentkit 0.2.0, `nearpay-agentkit` `stage-3/3.3-agentkit`).** Everything else is as specified above.
- **Tool set.** Merchant: `nearpay_create_checkout_session` (input = spec `CheckoutSessionCreate` shape + `idempotency_key`; validated with the spec schema incl. refinements; returns the session with `url`, without the separate `client_secret`), `nearpay_get_payment_intent`, `nearpay_list_payments` (spec `listPaymentIntents` query + `metadata` → `metadata[k]`). Payer: `nearpay_pay_checkout_session(url, max_amount?, wait_seconds?)`, `nearpay_fetch_paid(url, method?, headers?, body?, max_amount?, cross_chain?, max_wait_seconds?)`, plus `nearpay_resume_paid_fetch(operation_id, tx_hash?)` (continues a pending cross-chain operation, never deposits) and `nearpay_get_spending` (limits, allow-list, open operations; never tokens). Tool inputs are the spec's zod schemas (MCP SDK 1.32, zod 4), so they are not hand-written.
- **Merchant tools call the spec routes directly**, not through `@nearpay/node` (its 0.2.0 is unpublished and agentkit depends on the public spec only): `Bearer` key, `NearPay-Version`, `Idempotency-Key` on POST reused across retries, the node SDK's retry policy (429 / `idempotency_in_progress` always; network errors and 5xx only for replay-safe routes), tolerant response parsing.
- **Payer safety (fail closed).** Payer tools exist only with a signer **and** a non-empty pay-to allow-list (merchant Intents accounts: `requirement.pay_to`, x402 `payTo`, near-intents `extra.destination.recipient`). Limits per asset in base units: per call and per session; default 1.00 / 10.00 of the five known 6-decimal stablecoins (USDC/USDT on NEAR, USDC on Base, Arbitrum, Ethereum), every other asset refused until configured; `max_amount` only lowers the per-call limit. "Session" = the server process; over HTTP every client shares one budget (a client cannot reset it by opening a new MCP session). Budget accounting (`SpendingBudget` in agent-signer): reserve before signing/depositing, release only on a definite refusal (agent_pay 4xx; an x402 402 whose `PAYMENT-RESPONSE` is a non-pending failure; `DepositNotSentError`), otherwise commit — an unknown outcome counts as spent. Checkout and invoice URLs must be on configured pay hosts (default `pay.nearpay.money`), https only. The mode is fixed per server: sessions/invoices of the other mode are refused and the merchant key must match.
- **Invoice payments** read `getPublicInvoice` first (refused unless `payable` and of the agent's mode), then `createPublicInvoiceSession`; the returned client secret must belong to the returned session; then the unchanged checkout flow.
- **Evidence links.** x402: the settlement tx (`near:mainnet`), near-intents also the deposit tx (origin chain) and `extra.agentPayment`; checkout/invoice: the agent payment, checkout session, payment intent and invoice ids and the verified attestation (`kid`, destination fingerprint) — the payer API exposes no settlement tx (CR below). Explorer links (same table as kit `chains`) only in live mode; test-mode transactions are the sandbox's.
- **Secrets.** Keys, client/invoice secrets, operation tokens, `Bearer` tokens and configured literals are redacted from logs (JSON lines on stderr; stdout is the stdio protocol) and error results; success results never contain them by construction. The cross-chain operation store (file per operation) is 0700/0600.
- **HTTP transport.** Stateless (one MCP server object per POST, one shared context), bearer token ≥ 32 chars compared in constant time, loopback bind by default, `Host` allow-list (DNS rebinding), requests with a browser `Origin` refused unless allowed, 1 MiB bodies.
- **Signing.** NEP-413 with the operator's key (`ed25519:…` or a NEAR CLI credentials file); in test mode without an RPC URL the Verifier salt is static (the sandbox Verifier accepts any salt), live mode reads `current_salt`. Cross-chain origin wallets: `evmDepositor` (viem-style wallet clients; ERC-20 `transfer` or configured native coins, no memo) — the binary builds them with viem (optional peer) from a local EVM key and per-chain RPC URLs.
- **Paywall (`origins`).** The unquoted entries it issued are remembered in process by binding (until `deadline` + 60 s, bounded) and sent as `paymentRequirements`; on another replica (or after a restart) the client's `accepted` entry is sent after the local checks (unquoted form, destination amount/asset/recipient, configured origin and window, resource) — the facilitator compares it with the stored issued entry anyway (agentpay §4.2). A deposit arriving while the same operation is settling in this process is answered `settlement_pending`. A paywall without `origins` answers near-intents payloads `invalid_payment_requirements`; with `includeIntentsTransfer: false` it refuses intents-transfer payloads. The `Facilitator` interface's `nearIntents*` methods are optional (custom 0.1 facilitators keep compiling; `origins` requires them). `PaidRequest` / `X402PaymentEvent` are unions on `method`.
- **Client (`crossChain`).** Preference: intents-transfer when the signer exists and either no balance provider is configured, the balance (Verifier `mt_balance_of`) covers amount + fee, or the balance is unreadable (a refused transfer moves nothing); otherwise the first payable near-intents entry (origin signer can pay the network/asset, origin listed in `crossChain.origins` order if given, a spend limit exists for the origin asset, merchant allowed). The quoted entry must keep binding, scheme, network, asset, window, destination and origin asset; carry a positive `amount`, a deposit address and an operation token; `minAmountIn ≤ amount`; `refundDeadline` ≥ 120 s ahead (`minDepositWindowMs`). Operation states `depositing → deposited → settled | failed`, or `deposit_unknown` when the depositor failed without `DepositNotSentError` (resolved only by resuming with the tx hash). Any open operation (`depositing`, `deposit_unknown`, `deposited`) for the same resource URL blocks a new quote (a `deposited` one is resumed instead). Stored operations hold no request headers or body.

## 3. `nearpay-cli` (Stage 3)

Commands: `login` (device code via dashboard session → restricted test key stored in OS keychain), `listen --forward-to http://localhost:3000/webhooks` (consumes `GET /v1/events/stream`, re-signs with a local secret printed at start), `trigger <scenario>` (creates a test session and advances the sandbox), `events list|resend`, `logs tail`. Distributed via npm (`@nearpay/cli`) and single-file binaries (`bun build --compile`).

**Contracts (spec 0.3.0).**
- **`login`** — identity §6.2: `createCliLogin` → print `user_code`, open `verification_url_complete` (`--no-browser` prints it) → `pollCliLogin` every `interval` (honour `429 Retry-After`) until `approved` (store `key.secret` in the OS keychain, account id/name in the config file), `denied` or `expired`. The key is a restricted **test** key (`rk_test_…`, `CLI_KEY_SCOPES`, 90 days); `--api-key` / `NEARPAY_API_KEY` override it (a live key only works for commands whose routes accept live mode; `listen` refuses live keys). `logout` deletes the local copy and tells the user to revoke it in the dashboard (no key self-revocation route; dashboard sessions only).
- **`listen [--events t1,t2] [--forward-to URL]`** — `streamEvents` `GET /v1/events/stream?types=`: prints each `event` frame (type, id, object id), on `reset` warns and continues; reconnects with `Last-Event-ID` after the 1 h server close, a network error or a slow-client close (backoff 1 s → 30 s); dedupes by event id. `--forward-to` POSTs the event JSON with `NearPay-Signature` computed with a **local** `whsec_…` printed at start (same header format as webhooks §6, HMAC `v1` only; no `v1a`) plus `NearPay-Event-Id`/`NearPay-Event-Type`, so `@nearpay/node` `constructEvent` verifies with that secret. Types come from `WEBHOOK_TYPES` (payments, refunds, agent payments, accounts, reviews, and billing's `invoice.*` / `customer.subscription.*`).
- **`trigger <event>`** — fixtures of real API calls with the CLI key, never synthetic events: `checkout.session.completed` / `payment_intent.succeeded` (create session → `payCheckoutSessionTestHelper` outcome `succeeded`), `payment_intent.payment_failed` (`payment_failed`), `payment_intent.overpaid` (`amount_in` above the quote), `refund.*` (pay → `createRefund` → `simulateRefundDeposit`), `invoice.created|finalized|sent|paid` (billing: product/price → `createInvoice` → `finalizeInvoice` → `sendInvoice` → its `hosted_invoice_url` secret → `createPublicInvoiceSession` → `payCheckoutSessionTestHelper`), `invoice.voided`, `customer.subscription.created|updated|deleted` (billing routes). `customer.subscription.renewal_upcoming`, `invoice.overdue` and renewal invoices need a billing test helper that advances a subscription's clock — **not in spec 0.3.0** (open question for billing). `agent_payment.*` via `@nearpay/x402` against a sandbox-funded test signer (sandbox faucet) — no new route.
- **`events list|resend`** — `listEvents`, `resendEvent` (scopes in `CLI_KEY_SCOPES`). **`logs tail`** has no backing API in v1 (no request-log route); dropped from the Stage 3 CLI.

### 3.1 Implementation decisions (step 3.3, `nearpay-cli` 0.1.0)

1. **Client.** No SDK dependency: a ~250-line client driven by the `PUBLIC_ROUTES` definitions (requests validated with the route schemas before sending, responses parsed with `safeParseTolerant`, `ErrorEnvelope` → typed errors). `Idempotency-Key` on every POST and idempotent PATCH, reused across retries; safe requests retry network errors / 5xx / 429 (≤ 2, honouring `Retry-After`). `User-Agent: nearpay-cli/<v> node/<v> (<platform>; <arch>)`. Anonymous and client-secret routes never carry the key.
2. **Test mode only, fail closed.** `sk_live_`/`rk_live_`/`pk_` keys are refused before any request (exit 2). `login` refuses to store an approved key that is not `rk_test_…` with `livemode: false`. Key precedence `--api-key` > `NEARPAY_API_KEY` > profile (`--profile`, default `default`).
3. **Login polling.** Wait `interval` before every poll; `429` → interval += 5 s (RFC 8628 `slow_down`) and wait `max(interval, Retry-After)`; network errors / 5xx back off (×2, ≤ 60 s); `404` = expired; unknown `status` values keep polling. The local deadline is `min(expires_at − now, CLI_LOGIN_TTL_SECONDS)` (a skewed local clock neither stops early nor polls forever) and one last poll happens at the deadline. The browser opener only opens `https:` (or loopback `http:`) URLs, via argv (no shell).
4. **Credential storage.** OS keychain through `@napi-rs/keyring` (service `nearpay-cli`, account = profile; written then read back). The `0600` `credentials.json` fallback (directory `0700`, atomic write) is used only when the keychain library reports no platform store (`NoStorageAccess`) or cannot load; a keychain that exists but refuses (`PlatformFailure`, user cancel, locked) is an error. The fallback is warned at `login` and in `whoami`; a credentials file readable by group/other is refused. `config.json` holds the account, key id, masked key, expiry and which store holds the key — never the key.
5. **`whoami`.** No key-introspection route exists for restricted keys (identity's `GET /v1/account` and `/v1/api_keys` are session-only), so `whoami` shows the profile and proves the key with `listEvents?limit=1` (`events.read`).
6. **`listen`.** Own WHATWG SSE parser (CR/LF/CRLF split across chunks, BOM, `id` persistence). Reconnect also when no byte arrives for 3 heartbeats (45 s); backoff 1 s → 30 s ± 20 % jitter, reset once a stream is `ready`; `429` waits `Retry-After`; `401`, `403` (`livemode_forbidden`, `permission_denied`) and `400 event_type_unknown` are fatal. After a `reset` frame the stale cursor is dropped. Dedupe keeps the last 10 000 ids. Forwards are sequential (stream order), POST the `data:` payload byte for byte (an event this CLI's spec version cannot parse is still forwarded, with a warning), `redirect: manual`, 10 s timeout, never retried; `User-Agent: NearPay-CLI/<v> (listen)`. The local secret is `whsec_` + 40 base62 characters (rejection-sampled) — valid for the spec's `WebhookEndpoint.secret` format. `--events` types unknown to the CLI are passed on with a warning (the server decides). `--print-json` puts raw event JSON on stdout. Non-loopback `--forward-to` targets are allowed with a warning.
7. **`trigger` fixtures (supersedes the §3 bullet where they differ).** Sessions are USD-priced; the scenario is the pricing amount's last two digits (sandbox §4). `payment_intent.overpaid`: USD 10.06 session → helper `outcome: none` (open quote) → helper `succeeded` (scenario `06` pays the older quote → duplicate settlement); `amount_in` above the quote is **not** used — 1Click refunds the excess, so it would not overpay. `payment_intent.requires_review`: USD 10.05 (scenario `05`, short settlement). Refunds wait for the intent to succeed, then refund an amount ≤ `amount_settled` ending in `00` (or `04` for `refund.failed`), `simulateRefundDeposit` once the leg is prepared; `refund.canceled` via `cancelRefund`. `checkout.session.expired` via `expireCheckoutSession`. `payment_intent.canceled` needs `payment_intents.write`, which `CLI_KEY_SCOPES` lacks → works only with `--api-key sk_test_…`. Subscriptions use a 30-day trial (no first invoice/email); `.updated` sets `cancel_at_period_end`. **Not supported:** `agent_payment.*` (no public way to fund a sandbox agent signer in spec 0.3.0 — the sandbox faucet is internal), `invoice.overdue` / `customer.subscription.renewal_upcoming` (billing clock helper), `review.*`, `account.updated`, `ping`. After the fixture, `trigger` polls `listEvents?type=&created[gte]=` until the event about the target object exists (`--timeout`, default 90 s; exit 4 on timeout; `--no-wait`).
8. **Exit codes.** 0 ok, 1 error, 2 usage, 3 not logged in / key rejected / login denied or expired, 4 trigger timeout, 130 interrupted (`listen` exits 0 on Ctrl-C, its normal stop).
9. **Binaries.** `bun build --compile` embeds the host's `@napi-rs/keyring-<platform>` addon, so CI builds one binary per OS runner (Linux, macOS, Windows) instead of cross-compiling.
10. **Tests.** A spec-validating local mock (requests, responses and every SSE frame against spec 0.3.0; `rk_` scopes = `CLI_KEY_SCOPES`) and a stateful fake built on it (device login with `slow_down`, stream resume/`reset`, sandbox scenarios, refunds, billing); the integration suite runs the built binary and verifies forwarded events with `@nearpay/node` `constructEvent`.

**Step 2.3 decisions (implemented):**
- **No Starlight.** Starlight injects an inline theme script and Pagefind needs `wasm-unsafe-eval`, both incompatible with the strict CSP (`default-src 'none'; script-src 'self'; style-src 'self'`), and its styling would fight the `@nearpay-internal/ui` tokens. The docs use a small custom Astro layout on the kit's tokens, DM Sans and component CSS. Code blocks use Prism (class-based tokens; Shiki writes `style=""`). Astro never inlines CSS or scripts (`inlineStylesheets: never`, `assetsInlineLimit: 0`); `scripts/check-dist.mjs` fails the build on any inline script/style, style attribute, inline handler or third-party asset.
- **Two builds, one project:** `NP_SITE=web|docs` selects `src/routes/<site>/`, injected with `injectRoute` (no `src/pages`). Docs are served at the root of `docs.<domain>` so catalogue `doc_url`s (`/errors/<code>`) resolve.
- **Generated pages are rendered at build time** from the installed `@nearpay/spec` (`src/lib/spec.ts`): nothing generated is committed, so nothing can be hand-edited. `check-dist` asserts one page per catalogue code and that every public developer route appears in the reference.
- **Reference scope:** routes whose `x-nearpay.auth` includes a non-session credential (secret/restricted key, client secret, anonymous), except `/v1/auth/*`. Dashboard-session-only routes (account, team, API keys, settlement-destination changes, refund recipient override) are the dashboard's API and are not listed. Spec 0.2.0: 62 routes in 15 presentation groups (resource names; grouping and intros are presentation only).
- Event types page from `WEBHOOK_TYPES`; per-error "What to do" advice is hand-written (`error-notes.ts`), facts come from the catalogue. Search: a static `/search-index.json` (guides, groups, operations, error codes) and a 1.5 KB gz external script (also copy buttons); every page works without JavaScript (nested attributes and mobile navigation use `<details>`).

## Spec change requests from step 3.3 (agentkit)

- **CR-33-AK-01** `PayerAttempt` += optional nullable `settlement: {chain, tx_hash, explorer_url} | null` (from the attempt's evidence once verified): payer tools (MCP, checkout page) cannot return an on-chain evidence link for checkout/invoice payments today; merchants see it in `PaymentIntent.attempts[].evidence`.
- **CR-33-AK-02** `SettleResponse` (`intents-transfer`) += optional `extra: {agentPayment: ap_…}` (as `NearIntentsSettleResponse.extra.agentPayment`), so x402 payers can cite the merchant-side record.
