## 1. Dashboard (`dashboard.nearpay.<tld>`, static SPA)

- **Auth:** passkey login/registration (`@simplewebauthn/browser`) against identity; session cookie is same-origin (`/api` → gateway); CSRF token header on unsafe methods.
  - **Session restore (step 1.4, spec 0.1.5):** on load the app recovers the `DashboardSession` (incl. `csrf_token`) from the HttpOnly cookie with `getDashboardSession` (`GET /v1/auth/session`, identity §6) and waits for it before routing; `401` means signed out. The session is held in memory only — nothing (no CSRF token) is written to web storage — so a reload and a new tab both recover it. The `sessionStorage` copy that step 1.3 builds kept is deleted on load and never read.
  - **Responses:** the API client parses every JSON response with the spec's `safeParseTolerant(route.response)` (foundations §3); a contract break is reported as `invalid_response` instead of rendering malformed data.
  - **Session loss:** `401 authentication_required` or `403 csrf_token_invalid` → local sign-out and `/signin?next=`.
  - **Step-up:** a `401 step_up_required` from **any** route opens the WebAuthn modal; after `stepUpVerify` the original request is replayed once with the same `Idempotency-Key` (a double submit cannot create two objects). Cancel → the action shows "Confirmation canceled." and nothing is sent.
  - **Turnstile:** build-time site key `VITE_TURNSTILE_SITEKEY` (default: Cloudflare's test key). Only with the test key, if the widget cannot load (offline local stack), the documented dummy token `XXXX.DUMMY.TOKEN.XXXX` is sent (the paired test secret accepts it); a real site key never falls back.
- **Mode switch:** test/live toggle (stored in memory + URL `?mode=`); every request sends `NearPay-Mode: test|live` and identity's authz mints `lm` accordingly for session principals (identity §8.1). **Live-mode gate (L-DB-02):** identity enforces `live_enabled` only on routes declaring `account_not_live` (none is session-callable in Stage 1), so the UI additionally disables live-only writes (create/roll API key, create/update/test webhook endpoint) until `GET /v1/account/requirements` reports `live_enabled`. Onboarding (destinations, KYB, settings) and safety actions (revoke, delete, disable, logout) stay enabled — otherwise adding the first live destination would deadlock. Role gating is derived from the route `roles` in the spec.
- **Pages (stage):** Home (requirements checklist, recent payments) S1 · Payments list/detail (attempts timeline, evidence links to explorers) S1 · Settlement destinations (add → wallet attestation via NEAR Connect / EIP-191 → "Payout wallet active" at once (ADR-0027; neutral "Activating" copy only for an operator-set cool-off), fingerprint) S1 · Developers: API keys (create/roll/revoke), webhooks (endpoints, deliveries), events S1 · Agent payments S1 · Refunds (create; wallet signing of `next_action`; status) S2 · Team & approvals S2 · KYB S2 · Customers, payment links S2 · Invoices, subscriptions, products S3 · Mandates S4 · Settings (fee bearer, late payments, tolerance, branding) S1/S2.
- **Wallet signing (refunds, attestations):** builds exactly the payload returned by the API (`next_action` / challenge message) and shows a human-readable summary before signing; never edits recipient or amount.
  - **Attestation:** the dashboard signs exactly the challenge (`message`; NEP-413 `recipient` + base64 `nonce`) and refuses to sign when the wallet account ≠ the destination address (client-side check before the API's). NEP-413: the signature is passed as the wallet returns it (base64) with `public_key`; EIP-191: `personal_sign` of the UTF-8 hex message by the destination address.
  - A destination left in `pending_verification` whose challenge expired or is missing gets a new one with `challengeSettlementDestination` (`POST /v1/settlement_destinations/{id}/challenge`, spec 0.1.5; step-up through the usual `401` replay); earlier challenges stop being accepted (identity §6).
- **Webhook deliveries:** the delivery log (`listWebhookEndpointDeliveries`, spec 0.1.5, webhooks §5) is a card on the endpoint page — 20 per page with a cursor pager — not a separate route.
- **Payments detail:** the destination fingerprint is computed client-side with the spec algorithm (validated against `destination-fingerprint.json`; `DestinationSnapshot` has no `fingerprint` — requested). Evidence links use `Evidence.explorer_url` when https, else are derived for `near:mainnet` and known EVM chains; unknown or sandbox chains show the hash without a link. Money display uses bigint/string arithmetic only (INV-5), with asset decimals from `GET /v1/assets`.
- **CSP** (meta in `index.html`; `frame-ancestors` stays an nginx header): `script-src 'self' 'nonce-NPCSPNONCE' https://challenges.cloudflare.com`; `style-src 'self' 'unsafe-inline'` (NEAR Connect's popup uses inline styles); `connect-src 'self' https: wss:` (wallet executors call wallet and RPC hosts). NEAR Connect runs sandboxed wallets in `srcdoc` iframes that inherit the CSP, so nginx replaces `NPCSPNONCE` with the per-response `$request_id` (platform §1); injected and EVM wallets do not need the nonce. An unsubstituted `NPCSPNONCE` is never used as a nonce (`cspNonce()` returns undefined, NEAR wallets stay off). NEAR Connect uses the same pinned, SRI-checked wallet manifest as the checkout (`src/wallets/near-manifest.ts`; checkout-and-js §10).
- **Tests:** Playwright flows in testbed for signup → destination → key → webhook → test payment visible.

- **Stage 2 pages (step 2.1 contracts):** Team (`listMembers`, `updateMember`, `removeMember`, invitations; accept via `/auth/invite#token=` → `verifyMagicLink` for new users or `acceptInvitation` when signed in), account switcher (`listMemberships`, `switchSessionAccount`), destination approvals (`approveSettlementDestination`; `403 approver_conflict` explains that another owner/admin must approve), restricted keys (`createApiKey type: restricted` with a per-resource read/write matrix built from `KEY_SCOPES`; `updateApiKey`), KYB (form over `KybProfile` → `updateKybProfile`, `submitKyb` with the declaration checkbox; shows `requested_info` when `needs_info`; never claims third-party verification — ADR-0020; an approved case reads "You're live — you can accept real payments" (ADR-0024: approval is automatic on save; no "under review" / waiting copy, `pending` — manual mode only — reads "Submitted"; the registration number is optional and shows "Not provided"), never "verified identity" or "reviewed by NearPay", even though the API fields are named `kyb_verified` / `verified_legal_name`), audit log + CSV export (`listAccountAuditEvents`), webhook secret rotation and event resend.

- **Stage 2 feature modules (step 2.3):** each feature is a module under `src/features/<name>/` exporting `routes` (`name`, `pattern`, `title`, `crumb`, `nav`, `roles` from the spec read route, `render`) and `nav` metadata; core owns the shell and route registry. Routes: `/refunds`, `/refunds/:id`, `/payments/:id/refund` (Review refund), `/payment-links`, `/payment-links/new` (before `/:id`), `/payment-links/:id`, `/customers`, `/customers/:id`, `/settings/team`, `/settings/business` (KYB), `/settings/audit`, `/settings/appearance`; the payment page embeds `PaymentRefunds`.
  - **Refund signing:** "Review in wallet" creates the refund and opens the wallet review of `next_action`. Before any wallet prompt the dashboard checks the action is self-consistent (deadline not passed; asset = refund asset; amount > 0; for `sign_intent`: one `transfer` intent whose receiver/token/amount/memo equal `transfer`, `payload` and `nep413.message` are the same message, same nonce and signer) and refuses to sign otherwise; it never rebuilds or edits the payload. The summary shown is computed from those fields, with the API `display` alongside. `sign_intent`: NEAR wallets sign `nep413` verbatim (signature normalised to `ed25519:<base58>`), `0x` Intents accounts sign `payload` with ERC-191 (`v` normalised to 0/1) → `submit_tx {signed_intent}`. `sign_and_send`: on `eip155:*` chains without a memo, one ERC-20 `transfer` (or native send) of exactly `amount` to `to` from `from` (account and chain checked, chain switched and re-checked); every other chain uses the manual path (exact instructions + copyable address, then `submit_tx {tx_hash, sender?}`).
  - **Test-mode refunds never open a wallet:** test legs point at sandbox deposit addresses, so the dashboard offers only "Simulate signed transfer" (`simulateRefundDeposit`) in test mode — nothing is signed or broadcast.
  - Open refunds (preparing, submitted, pending) are polled every 5 s (higher `sequence` wins); `prepare`, `cancel` and the owner override (`updateRefundRecipient`, reason required, step-up) are offered per the spec state rules. Customers' "Total paid / Last payment" are summed client-side from `listPaymentIntents?customer=…&status=succeeded` (first 100, shown as "≥" when more exist) until the API offers totals. Checkout appearance saves `display_name` and `settings.branding.accent_color`; theme and corner style are preview-only until an account setting exists. Payment links and refunds are not live-gated (onboarding-safe); a live link created before `live_enabled` shows a notice.
- **Step 2.3 dashboard core (decisions):**
  - *Feature registry.* Every page area is a module discovered at build time (`src/features/<area>/module.tsx` → routes with `section` + `title`, sidebar slot, settings cards); the sidebar has fixed Figma slots (Overview, Payments, Payment links, Customers, Billing [Stage 3, hidden until `VITE_NP_STAGE` ≥ 3], Agent payments, Settlement, Developers, Settings) and a slot without a module is not shown. The Stage 2 areas (`index.ts` exports `routes`/`nav`) are code-split, loaded on first use; a unit test keeps the core route table equal to each area's exports. Kit links (`<a href>`) navigate through the History API via one delegated click handler.
  - *Live/Test.* A `switch` in the top bar (the Figma pill) replaces the two buttons; the live-only write set (L-DB-02) also covers the Stage 2 writes on the same objects: `updateApiKey`, `rotateWebhookEndpointSecret`, `resendEvent`.
  - *Overview numbers* come from `listPaymentIntents` (`created[gte]` window, ≤ 500 intents): settled volume in the most used fiat currency (bigint sums; other currencies counted, not converted), change vs the previous 7 days, completion share, reviews + processing > 30 min; no analytics endpoint in v1. With no payment in the mode and live mode off, Overview is the onboarding checklist (`/setup` always): 01 account, 02 destination (live), 03 business details (`/settings/business`, "Live as soon as you save them", ADR-0024), 04 test payment.
  - *Payments list.* ADR-0018 filters live in the URL (period → `created[gte]`, source, status, currency; "More filters": `amount[gte|lte]` only with a currency/pricing asset so amounts compare like with like, settlement asset, customer, payment link, checkout session, ≤ 10 `metadata[key]`). CSV export walks the filtered list client-side (≤ 1 000 rows, formula-injection guard, exact decimals).
  - *Payment detail* shows Purchase (gross), Payment fee (statement `fee.amount_estimated`, bearer) and You received (`amount_settled`) separately; the activity timeline is derived from the intent and its attempts. Payer wallet and the amount the payer sent are not in the contract (spec change requested), so the Figma's "Payer sent" / "Wallet 0x71…" are replaced by the fee stat and "Guest checkout".
  - *Destinations.* `pending_approval` rows show `approval` progress ("1 of 2 approvals") with Approve/Reject (`approveSettlementDestination`, step-up); the server decides the two-approver rule (`approver_conflict`), the UI only disables Approve for a user already in `approved_by`.
  - *Agent payments.* Paid resources are grouped from real x402 payments by `resource_url`; v1 has no resource registry, so "Add paid resource" validates name/URL/price/active Intents destination and produces the server code (`x402.requirements` → 402, `x402.settle` before serving).
  - *Dialogs.* Destructive actions use a confirmation dialog instead of `window.confirm`; the step-up dialog always stacks above the dialog whose request it replays.

- **Step 3.3 dashboard (decisions; spec 0.3.0, ui 0.3.0):**
  - *Modules.* Stage 3 areas are `module.tsx` feature modules with code-split pages (`lazyPage`, one chunk per page): `billing` (sidebar slot + shared hub/helpers), `invoices`, `subscriptions`, `products`, `tax-rates`, `cli`; `FEATURE_STAGE` defaults to 3. `RouteDef` gains `roles` (the spec route's roles; other roles get a notice, buttons are role-gated as before) and `layout: "focus"` (signed-in page without the shell). Routes: `/billing` (Invoices tab), `/billing/subscriptions`, `/billing/products`, `/billing/tax-rates` (tabs of one hub: stats + tab links, Figma b02), `/billing/invoices/new`, `/billing/invoices/:id[/edit]`, `/billing/subscriptions/new`, `/billing/subscriptions/:id`, `/billing/products/:id`, `/cli/authorize`, `/developers/live`.
  - *Hub stats* (no analytics endpoint): collected this month = Σ `amount_paid` of the first 100 `paid` invoices with `paid_at` in the month; outstanding = Σ `amount_remaining` of the first 100 `open` invoices; active subscriptions = count of `status=active` (≤ 100, "+" when capped). Sums per currency (bigint), the most frequent currency shown, others counted, never converted.
  - *Invoices.* "Past due" is a list filter (`status=open` + `due_date[lte]=now`) and a badge for open invoices past their due date; the API status stays `open`. The draft form previews totals with the spec's `computeInvoiceTotals` (per-line tax, round half-up); the server's totals are shown once saved. The first save creates the draft, later saves `PATCH` the same draft, so a failed finalize never creates duplicates. Due dates are local end-of-day. Send is disabled for 10 minutes after `status_transitions.sent_at` (countdown shown); a `429` still maps to "Emailed recently". PDF downloads use `ApiClient.download` (fetch with `NearPay-Mode`, Blob + `Content-Disposition` file name) — a plain link could not send the mode header. Activity = the invoice's public events (scan of `listEvents` since `created`, ≤ 300, filtered by `data.object.id`; every `invoice.sent` is visible) merged with `status_transitions` for what the 30-day event window no longer holds. Payments = `listPaymentIntents?invoice=`; a succeeded payment other than `payment_intent` on a paid/void invoice is flagged for refund (INV-3). No "mark paid" control (INV-2).
  - *Subscriptions.* The upcoming renewal invoice is estimated client-side: period = next `periodBoundary` after `current_period_end` (boundary 0 → 1 during a trial), items × price snapshot, item or default tax rates from `listTaxRates` (labelled as an estimate with today's prices; billing reprices at renewal, billing §12 d6); none for canceled, cancel-at-period-end, `unpaid` or `incomplete`. Dunning status = the latest invoice's `reminders_sent` / `reminder_days` / `next_reminder_at` plus the subscription's `on_exhausted`. Undo of a scheduled cancel = `updateSubscription {cancel_at_period_end: false}`.
  - *Catalogue.* Product creation creates the first price too (a retry after a failed price reuses the created product); prices are never edited (add + deactivate); tax percentages are typed as exact decimal strings (normalised, ≤ 4 decimals) with a worked example from `computeLineTax`.
  - *`/cli/authorize`* (identity §6.2): focus layout, reads `?code=` (normalised to `XXXX-XXXX`, else a code entry form), shows device, IP · country name, user agent, created/expiry and the account, asks to compare the code; Approve goes through the usual step-up replay; 404 → "not found / another account" copy, 409 → reload + "already handled", pending past `expires_at` shows as expired; roles without key access get an explanation and no request is made.
  - *Live tail* (webhooks §5.1): `EventSource` cannot send `NearPay-Mode`, so the stream is read with `fetch` + a WHATWG event-stream parser (`src/lib/sse.ts`) that reconnects like `EventSource` (server `retry`, `Last-Event-ID`; `429` waits `Retry-After`; other HTTP errors stop). Pause closes the stream and Resume reconnects with the last id (the server replays the gap); a filter change resumes from the last id; rows deduped by id, ≤ 200 kept; a mode switch remounts the page and opens a new stream; `reset` frames show "some events were skipped".
  - *Spec 0.2.1 CRs absorbed:* customer totals from `total_paid`/`last_payment_at` (client sums only for servers without them); `PaymentLink.name` (create, edit, list, detail); `branding.theme`/`corner_radius` saved (no longer preview-only); payment detail "Payer sent" from the paying attempt's `origin_amount` and "Payer address" from `refund_to`; `Member.security` in Team; `created_by` ("Added by") and the 7-day pending expiry / `disabled_reason: expired` on destinations; approver tenure explained in Team and Settlement.
- **Step 4.3 dashboard (decisions; spec 0.4.0, ui 0.3.1; billing §14, identity §20):**
  - *Modules.* `mandates` feature module (`/billing/mandates` = Billing hub tab "Auto-debit", `/billing/mandates/:id`), `FEATURE_STAGE` defaults to 4 (Stage 4 tab, routes and form options hidden below it). Mandate rows come only from `listMandates`/`getMandate` (billing §14 d1); nothing is created client-side.
  - *Collection method.* The subscription form offers "Email each invoice" / "Auto-debit" and explains eligibility before sending (billing §14 d2): USD → "USDC or USDT (1 USD = 1 token)"; asset price → only NEP-141, "works only if the vault allows <symbol>" (the API decides with `auto_debit_unavailable`); other fiat refused client-side; no active NEAR Intents destination in the mode → warning with a link to Settlement (not blocking: the destination is needed at prepare, `destination_not_intents_account`). The subscription page switches the method with `updateSubscription {collection_method}`; leaving auto-debit says the linked mandate is released and the customer is emailed how to cancel.
  - *Subscription panel.* Linked mandate = `Subscription.mandate`, else the newest `linked` + on-chain active + `collecting` one: status, balance + periods left, next collection, payer, last collection with evidence; low balance and keeper failures (`collect_failures`, 5-in-a-row rule) explained; unlinked mandates of the subscription each get the `unlinked_reason` in words and "NearPay never collects from it". **Amount-locked notice** while a linked mandate is active (§14 d6). Test mode: "Simulate customer funding" (`simulateMandateFunding`).
  - *Mandate page.* Stats (balance/periods left, next collection, collected periods), notices (unlinked, released, low balance, keeper failures, short collection with balance invoice, fee leg failed, canceled with refund, exhausted), collection history = paid invoices of the subscription with `Invoice.mandate_collection` (first 100) merged with `last_collection` (a short collection has no paid invoice), evidence = NEAR tx link (nearblocks in live; "(sandbox)" label in test — the stand-in is not on NEAR), terms (fee in bps and per period, expected share `floor(amount×(10000−fee_bps)/10000)`), accounts. Test helpers: `simulateMandatePayerAction` top up / cancel / withdraw.
  - *Merchant cancel* (§14 d9; dashboard §1 wallet-signing rule): `prepareMandateCancel` → `checkCancelTx` (exactly one `cancel({mandate_id: onchain_id})` on the mandate's vault, signer null or the merchant receiver, 1 yoctoNEAR) before any wallet prompt → human-readable summary (sign as, contract, call, gas · deposit, balance returned to the customer) → NEAR Connect `signAndSendTransaction` with the fields passed through verbatim (camelCase rename only), connected account must be the receiver; manual path = near-cli command + JSON. EVM-keyed (`0x…`) receivers can't sign NEAR transactions: explained, button disabled. Test mode never opens a wallet. After sending, the page polls `getMandate` (5 s, ≤ 2 min) and shows "canceled" only from the mirror (INV-2).

  - *Solana / Bitcoin destinations* (identity §20). Client-side checks before sending (from the same vectors as identity): Solana = base58 32 bytes, off-curve (PDA) addresses explained and refused in live mode ("Unverified destinations aren't available in the dashboard yet" — there is no public `mark_unverified` route; CR below), allowed in test mode; Bitcoin = bech32/bech32m checksum, HRP `bc`, single case, sent lower-case (note shown), P2PKH/P2SH/P2WSH refused with the reason (BIP-322 simple can't prove them). Attest: `standard: solana` via Wallet Standard discovery (`wallet-standard:app-ready`/`register-wallet` events, no library) and `solana:signMessage` over the exact UTF-8 bytes — the returned `signedMessage` must equal them (off-chain-header/SIWS wrappers refused), 64-byte signature sent base58; or a pasted base58 signature. `standard: bip322`: UniSat / OKX injected `signMessage(msg, "bip322-simple")` (connected address must match), else a pasted base64 signature (Sparrow, Xverse, Leather) whose witness shape is checked (P2WPKH 2 items with a 33-byte key, P2TR 1 item of 64/65 bytes) so the full/legacy formats are refused before sending. Explorer links: solscan, mempool.space.

## 2. Console (`ops.nearpay.<tld>`, internal SPA behind Cloudflare Access in server stage; local: separate port bound to localhost)

- **Auth:** `ptype=ops` sessions issued by identity for users in the `ops` allowlist with hardware-key passkeys; every action audited. Identity's authz already accepts console sessions; issuing them (ops sign-in) arrives with the console in Stage 2 (identity §8.1).
- **Pages:** Merchants (search, status, suspend/reinstate with two-person approval) · Businesses (KYB; ADR-0024: view, screening result, reject for abuse / reverse, link to suspend/reinstate; approve and request-info only in manual mode) · Compliance cases · Verifier holds & executions explorer (rails) · Sentinel findings & kill switch (engage; release requires second approver) · Reconciliation runs · Audit log.
- **Contracts (step 2.1):** the console uses only `OPS_ROUTES` from `@nearpay-internal/spec` (visibility `ops`, `/ops/…`), same-origin through `ops.<domain>/api` (identity §8.1). Sign-in: enrolment link (`/auth/enrol#token=`) → hardware passkey registration → `OpsSession` (held in memory; `getOpsSession` restores it); CSRF and the `401 step_up_required` replay work as in the dashboard (same `Idempotency-Key`). Role gating comes from each route's `opsRoles`; the UI never decides a two-person rule by itself — it shows `pending_request` / `pending_release` and the server answers `403 approver_conflict` when the same operator tries to approve. Pages → routes: Merchants (`listOpsMerchants`, `getOpsMerchant`, `getOpsMerchantSuspension`, suspension requests/approve/reject) · KYB (`listOpsKybCases`, `getOpsKybCase`, `decideOpsKybCase`) · Cases (`listOpsCases`, `getOpsCase`, assign/comment/close) and blocklist/screening (`listOpsBlocklist`, add/remove, `createOpsScreening`, `createOpsRescreen`) · Holds & executions (`listOpsExecutions` with `state=held` — `livemode` is required, the page has a live/test toggle and never mixes modes; `getOpsExecution`, `listOpsExecutionObservations` for the evidence trail, `reverifyOpsExecution` (step-up) to ask the Verifier to re-check a `held`/`verifying` execution — it never forces a state) · Sentinel (`getOpsKillSwitch`, engage, release request/approve/reject, `listOpsKillSwitchLog`, findings list/get/acknowledge) · Reconciliation runs (served by payments: `listOpsReconciliationRuns`, `getOpsReconciliationRun`, `createOpsReconciliationRun` for a re-run, `resolveOpsReconciliationRun` with step-up; a `diff`/`error` run also appears in Cases as `reconciliation_diff`, closed there after the run is resolved) · Refund view (`getOpsRefund`, linked from executions with `kind=refund`) · Audit log (`listOpsAuditEvents` — one trail: identity's own entries plus the operator actions compliance and sentinel publish as `ops_action.recorded` events).
- **Console implementation (step 2.3):**
  - **CSP:** `default-src 'none'`; `script-src`/`style-src`/`font-src`/`img-src`/`connect-src 'self'`; no nonce, no `'unsafe-inline'`, no `'unsafe-eval'` (the console loads no wallet, Turnstile or third-party code). zod runs `jitless` (set on `globalThis.__zod_globalConfig` before `@nearpay-money/spec` loads) so its `new Function` probe never trips the CSP. nginx adds `frame-ancestors 'none'`, `Cache-Control: no-store`, `noindex`.
  - **Session expiry:** the console ends the session locally at `min(max(idle_expires_at, last successful call + 30 min), expires_at)` and warns 2 minutes before (stay signed in = `getOpsSession`; not offered for the 12 h absolute end); any `401`/`403 csrf_token_invalid` signs out at once. The sign-in page explains why and returns to `?next=` (same-origin paths only). Nothing is written to web storage; merchant names are cached in memory per session.
  - **Navigation:** Overview · Merchants · Businesses (KYB; opens on active businesses, ADR-0024) · Cases · Payment holds · Reconciliation · Audit log, and Risk controls: Sentinel (kill switch + findings) · Blocklist (+ screening lookup, re-screen). The global working mode (`?mode=test`, default live) scopes executions, cases, findings and reconciliation lists; the kill-switch banner shows on every page while engaged.
