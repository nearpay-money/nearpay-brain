# LLD — `nearpay-dashboard` and `nearpay-console`

> Version 1.2 (step 1.3 implementation findings folded into §1) · Version 1.1 audited (`audits/dashboard-and-console.md`) · Foundations `00-foundations.md` · Identity LLD §6

## 1. Dashboard (`dashboard.nearpay.<tld>`, static SPA)

- **Auth:** passkey login/registration (`@simplewebauthn/browser`) against identity; session cookie is same-origin (`/api` → gateway); CSRF token header on unsafe methods.
  - **Session restore:** spec 0.1.4 has no "current session" route and the CSRF token is only in the sign-in response, so the `DashboardSession` (incl. `csrf_token`) is kept in memory + `sessionStorage` (tab-scoped); a new tab, or a stored session the API rejects, signs in again with a passkey. `GET /v1/auth/session` is requested for spec 0.1.5 (identity can re-issue the CSRF token from `csrf_enc`).
  - **Session loss:** `401 authentication_required` or `403 csrf_token_invalid` → local sign-out and `/signin?next=`.
  - **Step-up:** a `401 step_up_required` from **any** route opens the WebAuthn modal; after `stepUpVerify` the original request is replayed once with the same `Idempotency-Key` (a double submit cannot create two objects). Cancel → the action shows "Confirmation canceled." and nothing is sent.
  - **Turnstile:** build-time site key `VITE_TURNSTILE_SITEKEY` (default: Cloudflare's test key). Only with the test key, if the widget cannot load (offline local stack), the documented dummy token `XXXX.DUMMY.TOKEN.XXXX` is sent (the paired test secret accepts it); a real site key never falls back.
- **Mode switch:** test/live toggle (stored in memory + URL `?mode=`); every request sends `NearPay-Mode: test|live` and identity's authz mints `lm` accordingly for session principals (identity §8.1). **Live-mode gate (L-DB-02):** identity enforces `live_enabled` only on routes declaring `account_not_live` (none is session-callable in Stage 1), so the UI additionally disables live-only writes (create/roll API key, create/update/test webhook endpoint) until `GET /v1/account/requirements` reports `live_enabled`. Onboarding (destinations, KYB, settings) and safety actions (revoke, delete, disable, logout) stay enabled — otherwise adding the first live destination would deadlock. Role gating is derived from the route `roles` in the spec.
- **Pages (stage):** Home (requirements checklist, recent payments) S1 · Payments list/detail (attempts timeline, evidence links to explorers) S1 · Settlement destinations (add → wallet attestation via NEAR Connect / EIP-191, cool-off status, fingerprint) S1 · Developers: API keys (create/roll/revoke), webhooks (endpoints, deliveries), events S1 · Agent payments S1 · Refunds (create; wallet signing of `next_action`; status) S2 · Team & approvals S2 · KYB S2 · Customers, payment links S2 · Invoices, subscriptions, products S3 · Mandates S4 · Settings (fee bearer, late payments, tolerance, branding) S1/S2.
- **Wallet signing (refunds, attestations):** builds exactly the payload returned by the API (`next_action` / challenge message) and shows a human-readable summary before signing; never edits recipient or amount.
  - **Attestation:** the dashboard signs exactly the challenge (`message`; NEP-413 `recipient` + base64 `nonce`) and refuses to sign when the wallet account ≠ the destination address (client-side check before the API's). NEP-413: the signature is passed as the wallet returns it (base64) with `public_key`; EIP-191: `personal_sign` of the UTF-8 hex message by the destination address.
  - The attestation challenge is returned only on create; a destination left in `pending_verification` cannot get a new one (the UI says: disable and re-add). `POST /v1/settlement_destinations/{id}/challenge` is requested for spec 0.1.5.
- **Webhook deliveries:** `GET /v1/webhook_endpoints/{id}/deliveries` is not in spec 0.1.4 (webhooks Stage 2), so the endpoint page shows the test-ping result and a note; the route is requested for spec 0.1.5.
- **Payments detail:** the destination fingerprint is computed client-side with the spec algorithm (validated against `destination-fingerprint.json`; `DestinationSnapshot` has no `fingerprint` — requested). Evidence links use `Evidence.explorer_url` when https, else are derived for `near:mainnet` and known EVM chains; unknown or sandbox chains show the hash without a link. Money display uses bigint/string arithmetic only (INV-5), with asset decimals from `GET /v1/assets`.
- **CSP** (meta in `index.html`; `frame-ancestors` stays an nginx header): `script-src 'self' 'nonce-NPCSPNONCE' https://challenges.cloudflare.com`; `style-src 'self' 'unsafe-inline'` (NEAR Connect's popup uses inline styles); `connect-src 'self' https: wss:` (wallet executors call wallet and RPC hosts). NEAR Connect runs sandboxed wallets in `srcdoc` iframes that inherit the CSP, so nginx replaces `NPCSPNONCE` with the per-response `$request_id` (platform §1); injected and EVM wallets do not need the nonce.
- **Tests:** Playwright flows in testbed for signup → destination → key → webhook → test payment visible.

## 2. Console (`ops.nearpay.<tld>`, internal SPA behind Cloudflare Access in server stage; local: separate port bound to localhost)

- **Auth:** `ptype=ops` sessions issued by identity for users in the `ops` allowlist with hardware-key passkeys; every action audited. Identity's authz already accepts console sessions; issuing them (ops sign-in) arrives with the console in Stage 2 (identity §8.1).
- **Pages:** Merchants (search, status, suspend/reinstate with two-person approval) · KYB decisions (Stage 1 manual approve/reject) · Compliance cases · Verifier holds & executions explorer (rails) · Sentinel findings & kill switch (engage; release requires second approver) · Reconciliation runs · Audit log.
- **Stage mapping:** Stage 1 ships the ops **CLI** in `nearpay-testbed/ops` (`pnpm ops …`, platform §3) wrapping each service's in-container `dist/ops.js` (KYB decision, kill switch, cool-off skip, account show, rails flags) instead of UI; console UI arrives in Stage 2.
