## 1. Dashboard (`dashboard.nearpay.<tld>`, static SPA)

- **Auth:** passkey login/registration (`@simplewebauthn/browser`) against identity; session cookie is same-origin (`/api` → gateway); CSRF token header on unsafe methods.
  - **Session restore (step 1.4, spec 0.1.5):** on load the app recovers the `DashboardSession` (incl. `csrf_token`) from the HttpOnly cookie with `getDashboardSession` (`GET /v1/auth/session`, identity §6) and waits for it before routing; `401` means signed out. The session is held in memory only — nothing (no CSRF token) is written to web storage — so a reload and a new tab both recover it. The `sessionStorage` copy that step 1.3 builds kept is deleted on load and never read.
  - **Responses:** the API client parses every JSON response with the spec's `safeParseTolerant(route.response)` (foundations §3); a contract break is reported as `invalid_response` instead of rendering malformed data.
  - **Session loss:** `401 authentication_required` or `403 csrf_token_invalid` → local sign-out and `/signin?next=`.
  - **Step-up:** a `401 step_up_required` from **any** route opens the WebAuthn modal; after `stepUpVerify` the original request is replayed once with the same `Idempotency-Key` (a double submit cannot create two objects). Cancel → the action shows "Confirmation canceled." and nothing is sent.
  - **Turnstile:** build-time site key `VITE_TURNSTILE_SITEKEY` (default: Cloudflare's test key). Only with the test key, if the widget cannot load (offline local stack), the documented dummy token `XXXX.DUMMY.TOKEN.XXXX` is sent (the paired test secret accepts it); a real site key never falls back.
- **Mode switch:** test/live toggle (stored in memory + URL `?mode=`); every request sends `NearPay-Mode: test|live` and identity's authz mints `lm` accordingly for session principals (identity §8.1). **Live-mode gate (L-DB-02):** identity enforces `live_enabled` only on routes declaring `account_not_live` (none is session-callable in Stage 1), so the UI additionally disables live-only writes (create/roll API key, create/update/test webhook endpoint) until `GET /v1/account/requirements` reports `live_enabled`. Onboarding (destinations, KYB, settings) and safety actions (revoke, delete, disable, logout) stay enabled — otherwise adding the first live destination would deadlock. Role gating is derived from the route `roles` in the spec.
- **Pages (stage):** Home (requirements checklist, recent payments) S1 · Payments list/detail (attempts timeline, evidence links to explorers) S1 · Settlement destinations (add → wallet attestation via NEAR Connect / EIP-191, cool-off status, fingerprint) S1 · Developers: API keys (create/roll/revoke), webhooks (endpoints, deliveries), events S1 · Agent payments S1 · Refunds (create; wallet signing of `next_action`; status) S2 · Team & approvals S2 · KYB S2 · Customers, payment links S2 · Invoices, subscriptions, products S3 · Mandates S4 · Settings (fee bearer, late payments, tolerance, branding) S1/S2.
- **Wallet signing (refunds, attestations):** builds exactly the payload returned by the API (`next_action` / challenge message) and shows a human-readable summary before signing; never edits recipient or amount.
  - **Attestation:** the dashboard signs exactly the challenge (`message`; NEP-413 `recipient` + base64 `nonce`) and refuses to sign when the wallet account ≠ the destination address (client-side check before the API's). NEP-413: the signature is passed as the wallet returns it (base64) with `public_key`; EIP-191: `personal_sign` of the UTF-8 hex message by the destination address.
  - A destination left in `pending_verification` whose challenge expired or is missing gets a new one with `challengeSettlementDestination` (`POST /v1/settlement_destinations/{id}/challenge`, spec 0.1.5; step-up through the usual `401` replay); earlier challenges stop being accepted (identity §6).
- **Webhook deliveries:** the delivery log (`listWebhookEndpointDeliveries`, spec 0.1.5, webhooks §5) is a card on the endpoint page — 20 per page with a cursor pager — not a separate route.
- **Payments detail:** the destination fingerprint is computed client-side with the spec algorithm (validated against `destination-fingerprint.json`; `DestinationSnapshot` has no `fingerprint` — requested). Evidence links use `Evidence.explorer_url` when https, else are derived for `near:mainnet` and known EVM chains; unknown or sandbox chains show the hash without a link. Money display uses bigint/string arithmetic only (INV-5), with asset decimals from `GET /v1/assets`.
- **CSP** (meta in `index.html`; `frame-ancestors` stays an nginx header): `script-src 'self' 'nonce-NPCSPNONCE' https://challenges.cloudflare.com`; `style-src 'self' 'unsafe-inline'` (NEAR Connect's popup uses inline styles); `connect-src 'self' https: wss:` (wallet executors call wallet and RPC hosts). NEAR Connect runs sandboxed wallets in `srcdoc` iframes that inherit the CSP, so nginx replaces `NPCSPNONCE` with the per-response `$request_id` (platform §1); injected and EVM wallets do not need the nonce. An unsubstituted `NPCSPNONCE` is never used as a nonce (`cspNonce()` returns undefined, NEAR wallets stay off). NEAR Connect uses the same pinned, SRI-checked wallet manifest as the checkout (`src/wallets/near-manifest.ts`; checkout-and-js §10).
- **Tests:** Playwright flows in testbed for signup → destination → key → webhook → test payment visible.

- **Stage 2 pages (step 2.1 contracts):** Team (`listMembers`, `updateMember`, `removeMember`, invitations; accept via `/auth/invite#token=` → `verifyMagicLink` for new users or `acceptInvitation` when signed in), account switcher (`listMemberships`, `switchSessionAccount`), destination approvals (`approveSettlementDestination`; `403 approver_conflict` explains that another owner/admin must approve), restricted keys (`createApiKey type: restricted` with a per-resource read/write matrix built from `KEY_SCOPES`; `updateApiKey`), KYB (form over `KybProfile` → `updateKybProfile`, `submitKyb` with the declaration checkbox; shows `requested_info` when `needs_info`; never claims third-party verification — ADR-0020; an approved case reads "Business details reviewed by NearPay", never "verified identity", even though the API fields are named `kyb_verified` / `verified_legal_name`), audit log + CSV export (`listAccountAuditEvents`), webhook secret rotation and event resend.

- **Stage 2 feature modules (step 2.3):** each feature is a module under `src/features/<name>/` exporting `routes` (`name`, `pattern`, `title`, `crumb`, `nav`, `roles` from the spec read route, `render`) and `nav` metadata; core owns the shell and route registry. Routes: `/refunds`, `/refunds/:id`, `/payments/:id/refund` (Review refund), `/payment-links`, `/payment-links/new` (before `/:id`), `/payment-links/:id`, `/customers`, `/customers/:id`, `/settings/team`, `/settings/business` (KYB), `/settings/audit`, `/settings/appearance`; the payment page embeds `PaymentRefunds`.
  - **Refund signing:** "Review in wallet" creates the refund and opens the wallet review of `next_action`. Before any wallet prompt the dashboard checks the action is self-consistent (deadline not passed; asset = refund asset; amount > 0; for `sign_intent`: one `transfer` intent whose receiver/token/amount/memo equal `transfer`, `payload` and `nep413.message` are the same message, same nonce and signer) and refuses to sign otherwise; it never rebuilds or edits the payload. The summary shown is computed from those fields, with the API `display` alongside. `sign_intent`: NEAR wallets sign `nep413` verbatim (signature normalised to `ed25519:<base58>`), `0x` Intents accounts sign `payload` with ERC-191 (`v` normalised to 0/1) → `submit_tx {signed_intent}`. `sign_and_send`: on `eip155:*` chains without a memo, one ERC-20 `transfer` (or native send) of exactly `amount` to `to` from `from` (account and chain checked, chain switched and re-checked); every other chain uses the manual path (exact instructions + copyable address, then `submit_tx {tx_hash, sender?}`).
  - **Test-mode refunds never open a wallet:** test legs point at sandbox deposit addresses, so the dashboard offers only "Simulate signed transfer" (`simulateRefundDeposit`) in test mode — nothing is signed or broadcast.
  - Open refunds (preparing, submitted, pending) are polled every 5 s (higher `sequence` wins); `prepare`, `cancel` and the owner override (`updateRefundRecipient`, reason required, step-up) are offered per the spec state rules. Customers' "Total paid / Last payment" are summed client-side from `listPaymentIntents?customer=…&status=succeeded` (first 100, shown as "≥" when more exist) until the API offers totals. Checkout appearance saves `display_name` and `settings.branding.accent_color`; theme and corner style are preview-only until an account setting exists. Payment links and refunds are not live-gated (onboarding-safe); a live link created before `live_enabled` shows a notice.
- **Step 2.3 dashboard core (decisions):**
  - *Feature registry.* Every page area is a module discovered at build time (`src/features/<area>/module.tsx` → routes with `section` + `title`, sidebar slot, settings cards); the sidebar has fixed Figma slots (Overview, Payments, Payment links, Customers, Billing [Stage 3, hidden until `VITE_NP_STAGE` ≥ 3], Agent payments, Settlement, Developers, Settings) and a slot without a module is not shown. The Stage 2 areas (`index.ts` exports `routes`/`nav`) are code-split, loaded on first use; a unit test keeps the core route table equal to each area's exports. Kit links (`<a href>`) navigate through the History API via one delegated click handler.
  - *Live/Test.* A `switch` in the top bar (the Figma pill) replaces the two buttons; the live-only write set (L-DB-02) also covers the Stage 2 writes on the same objects: `updateApiKey`, `rotateWebhookEndpointSecret`, `resendEvent`.
  - *Overview numbers* come from `listPaymentIntents` (`created[gte]` window, ≤ 500 intents): settled volume in the most used fiat currency (bigint sums; other currencies counted, not converted), change vs the previous 7 days, completion share, reviews + processing > 30 min; no analytics endpoint in v1. With no payment in the mode and live mode off, Overview is the onboarding checklist (`/setup` always): 01 account, 02 destination (live), 03 business details (`/settings/business`, "Reviewed by NearPay"), 04 test payment.
  - *Payments list.* ADR-0018 filters live in the URL (period → `created[gte]`, source, status, currency; "More filters": `amount[gte|lte]` only with a currency/pricing asset so amounts compare like with like, settlement asset, customer, payment link, checkout session, ≤ 10 `metadata[key]`). CSV export walks the filtered list client-side (≤ 1 000 rows, formula-injection guard, exact decimals).
  - *Payment detail* shows Purchase (gross), Payment fee (statement `fee.amount_estimated`, bearer) and You received (`amount_settled`) separately; the activity timeline is derived from the intent and its attempts. Payer wallet and the amount the payer sent are not in the contract (spec change requested), so the Figma's "Payer sent" / "Wallet 0x71…" are replaced by the fee stat and "Guest checkout".
  - *Destinations.* `pending_approval` rows show `approval` progress ("1 of 2 approvals") with Approve/Reject (`approveSettlementDestination`, step-up); the server decides the two-approver rule (`approver_conflict`), the UI only disables Approve for a user already in `approved_by`.
  - *Agent payments.* Paid resources are grouped from real x402 payments by `resource_url`; v1 has no resource registry, so "Add paid resource" validates name/URL/price/active Intents destination and produces the server code (`x402.requirements` → 402, `x402.settle` before serving).
  - *Dialogs.* Destructive actions use a confirmation dialog instead of `window.confirm`; the step-up dialog always stacks above the dialog whose request it replays.

## 2. Console (`ops.nearpay.<tld>`, internal SPA behind Cloudflare Access in server stage; local: separate port bound to localhost)

- **Auth:** `ptype=ops` sessions issued by identity for users in the `ops` allowlist with hardware-key passkeys; every action audited. Identity's authz already accepts console sessions; issuing them (ops sign-in) arrives with the console in Stage 2 (identity §8.1).
- **Pages:** Merchants (search, status, suspend/reinstate with two-person approval) · KYB decisions (Stage 1 manual approve/reject) · Compliance cases · Verifier holds & executions explorer (rails) · Sentinel findings & kill switch (engage; release requires second approver) · Reconciliation runs · Audit log.
- **Contracts (step 2.1):** the console uses only `OPS_ROUTES` from `@nearpay-internal/spec` (visibility `ops`, `/ops/…`), same-origin through `ops.<domain>/api` (identity §8.1). Sign-in: enrolment link (`/auth/enrol#token=`) → hardware passkey registration → `OpsSession` (held in memory; `getOpsSession` restores it); CSRF and the `401 step_up_required` replay work as in the dashboard (same `Idempotency-Key`). Role gating comes from each route's `opsRoles`; the UI never decides a two-person rule by itself — it shows `pending_request` / `pending_release` and the server answers `403 approver_conflict` when the same operator tries to approve. Pages → routes: Merchants (`listOpsMerchants`, `getOpsMerchant`, `getOpsMerchantSuspension`, suspension requests/approve/reject) · KYB (`listOpsKybCases`, `getOpsKybCase`, `decideOpsKybCase`) · Cases (`listOpsCases`, `getOpsCase`, assign/comment/close) and blocklist/screening (`listOpsBlocklist`, add/remove, `createOpsScreening`, `createOpsRescreen`) · Holds & executions (`listOpsExecutions` with `state=held` — `livemode` is required, the page has a live/test toggle and never mixes modes; `getOpsExecution`, `listOpsExecutionObservations` for the evidence trail, `reverifyOpsExecution` (step-up) to ask the Verifier to re-check a `held`/`verifying` execution — it never forces a state) · Sentinel (`getOpsKillSwitch`, engage, release request/approve/reject, `listOpsKillSwitchLog`, findings list/get/acknowledge) · Reconciliation runs (served by payments: `listOpsReconciliationRuns`, `getOpsReconciliationRun`, `createOpsReconciliationRun` for a re-run, `resolveOpsReconciliationRun` with step-up; a `diff`/`error` run also appears in Cases as `reconciliation_diff`, closed there after the run is resolved) · Refund view (`getOpsRefund`, linked from executions with `kind=refund`) · Audit log (`listOpsAuditEvents` — one trail: identity's own entries plus the operator actions compliance and sentinel publish as `ops_action.recorded` events).
- **Console implementation (step 2.3):**
  - **CSP:** `default-src 'none'`; `script-src`/`style-src`/`font-src`/`img-src`/`connect-src 'self'`; no nonce, no `'unsafe-inline'`, no `'unsafe-eval'` (the console loads no wallet, Turnstile or third-party code). zod runs `jitless` (set on `globalThis.__zod_globalConfig` before `@nearpay/spec` loads) so its `new Function` probe never trips the CSP. nginx adds `frame-ancestors 'none'`, `Cache-Control: no-store`, `noindex`.
  - **Session expiry:** the console ends the session locally at `min(max(idle_expires_at, last successful call + 30 min), expires_at)` and warns 2 minutes before (stay signed in = `getOpsSession`; not offered for the 12 h absolute end); any `401`/`403 csrf_token_invalid` signs out at once. The sign-in page explains why and returns to `?next=` (same-origin paths only). Nothing is written to web storage; merchant names are cached in memory per session.
  - **Navigation:** Overview · Merchants · Business reviews (KYB) · Cases · Payment holds · Reconciliation · Audit log, and Risk controls: Sentinel (kill switch + findings) · Blocklist (+ screening lookup, re-screen). The global working mode (`?mode=test`, default live) scopes executions, cases, findings and reconciliation lists; the kill-switch banner shows on every page while engaged.
  - **Review screen** (Figma "Review RV-xxxx", an execution in `held`): checks are derived only from the execution's evidence fields (payer transfer = deposit tx / evidence; destination amount = evidence vs `settlement.expected`; independent confirmation = evidence tier A/B; merchant notification = linked `held_execution` case `review`). "Request investigation" = `reverifyOpsExecution` with the decision note (required); "Escalate case" = assign the linked case to the operator + comment the note. No mark-paid control exists.
  - **References:** short display refs are prefix + last four id characters (`RV–` held execution/case, `KY–` KYB, `RC–` reconciliation, `SC–` screening, `AU–` finding, `NP–` payment, `RF–` refund); full ids are shown with a copy button on detail pages.
  - **Amounts:** OPS_ROUTES have no asset registry and `Execution`/`ReconciliationTotals` carry no decimals, so the console formats the v1 settlement assets from a pinned display table and shows any other asset as exact base units (never a guessed decimal point). Spec request: `listOpsAssets` or `decimals` on those objects.
  - **Reconciliation report:** CSV built in the browser from `listOpsReconciliationRuns` (current filters, ≤ 1,000 runs): one row per run and asset with exact base units and display amounts; formula-leading cells are neutralised.
- **Stage mapping:** Stage 1 ships the ops **CLI** in `nearpay-testbed/ops` (`pnpm ops …`, platform §3) wrapping each service's in-container `dist/ops.js` (KYB decision, kill switch, cool-off skip, account show, rails flags) instead of UI; console UI arrives in Stage 2.

## Spec 0.2.1 contract changes (step 2.2/2.3 change requests, `nearpay-spec/CHANGELOG.md`)

- Dashboard: `PaymentAttemptSummary.refund_to` / `origin_amount` (payer address and amount sent; there is no "sending wallet" — 1Click reports none), `Customer.total_paid` / `last_payment_at` (replace the client-side sums), `PaymentLink.name`, `settings.branding.theme` / `corner_radius` (no longer preview-only), `Account.website`, `SettlementDestination.created_by`, `Member.security`, `disabled_reason: expired`.
- Console: `decimals` on `Execution.origin`/`settlement` and `ReconciliationTotals` (replace the pinned table; fall back to base units when absent), `account_display_name` on cases, reconciliation runs and findings, `listOpsCases` `subject`. List counts were not added (`has_more` → "N+").
